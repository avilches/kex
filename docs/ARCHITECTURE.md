# Kex - Architecture and Technical Reference

Kex is a lightweight, open-source terminal emulator. ~7-8 MB on disk. No telemetry. No account.

This document is the canonical reference for understanding how Kex works - both technically and from the user's perspective. It covers architecture, feature semantics, known limitations, and technical decisions that have observable effects on usage.

## 1. What Kex is and is not

**Is:** a fast, terminal-first development workspace with a native PTY backend, an integrated code editor, file explorer, and source control.

**Is not:**
- A full IDE replacement. No language-server integration, integrated debuggers, or refactoring engines at IDE scale.
- A general-purpose browser. The web preview pane is scoped to local dev servers and lightweight doc viewing only.
- A cloud product. No accounts, no telemetry, no managed sessions.
- A shell replacement. It runs your shell (zsh, bash, fish, pwsh) via a real PTY, it does not replace it.

## 2. High-level architecture

Kex uses a strict **two-process model**. The Rust process owns all OS access. The WebView (React) never touches the filesystem, processes, shells, or the network directly - everything goes through typed IPC calls (`invoke()`) to Tauri commands registered in `src-tauri/src/lib.rs`.

```
┌─────────────────────────────────────────────────────────────┐
│  Tauri process (Rust)                                       │
│                                                             │
│  pty::*         - PTY sessions (portable-pty)               │
│  fs::*          - Filesystem (read, write, search, watch)   │
│  git::*         - Git operations (subprocess)               │
│  shell::*       - Oneshot commands, persistent sessions,    │
│                   background processes                      │
│  workspace::*   - Auth registry + WSL bridge                │
│  history::*     - Shell history (suggest, record, list)     │
│  agent::*       - hooks/plugin installers, session store +  │
│                   per-provider restore table                 │
│                                                             │
└──────────────────────────┬──────────────────────────────────┘
                           │ invoke() / Tauri channels / events
┌──────────────────────────▼──────────────────────────────────┐
│  WebView (React + TypeScript)                               │
│                                                             │
│  terminal/      - xterm.js (WebGL), PTY bridge, OSC parsing │
│  editor/        - CodeMirror 6, diffs                       │
│  explorer/      - File tree, fuzzy search                   │
│  source-control/  - Git stage/commit/push UI                │
│  git-history/   - Commit graph, per-file diffs              │
│  theme/         - CSS variable engine, presets              │
│  agents/        - Terminal agent notifications              │
│  + tabs, header, sidebar, settings, preview…                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

There are two separate WebView windows: the main window (`index.html`) and the settings window (`settings.html`). Both run against the same Rust process state.

## 3. Features - user perspective

### 3.1 Terminal

**Workspace/Pane/Tab model.** The center area uses a three-level hierarchy: Workspaces (listed in a 52px vertical sidebar on the left) contain a binary pane tree; each pane holds a tab strip of tabs. Tabs are never unmounted when you switch between them - each PTY keeps receiving output in the background. Switching to a tab that has been running a command shows you the complete, up-to-date buffer instantly.

A workspace that reaches zero tabs folds away with its last tab, whatever the path: the tab close button or `tab.close`, the shell exiting on its own, moving or dragging the last tab to another workspace, and bulk closes such as Close All Tabs. The fold is a reconciliation effect in `useWorkspaces` (`emptyWorkspaceToClose`) that closes the empty workspace on committed state, so batched closes inside one tick are covered too, and the active workspace selection is reused from `closeWorkspace`. Two exceptions keep the workspace with an empty sole pane, which renders a welcome screen with quick actions (new terminal, open file): the window's only workspace (folding it would close the window), and a workspace holding Actions with a command, whose deletion the close confirmation dialog still protects. A workspace is also removed by an explicit close action (the dedicated `workspace.close` shortcut, the `tab.close` shortcut on an empty workspace, or the sidebar close button), routed through `requestCloseWorkspace`. The `tab.close` shortcut is contextual (it closes the focused tab or pane first, falling back to the workspace only when the pane is empty), whereas `workspace.close` always targets the active workspace. The close action reuses the hibernate dialog in `close` mode (`useCloseWorkspaceFlow`, `HibernateDialog`). The dialog opens only when something would be lost: the workspace has Actions with a command (it says how many will be deleted), documents with unsaved changes (each with its own Save button, plus Save all above two), agents or scripts still running, or terminals with a live foreground process (`collectRunningTerminals` + `leafHasForegroundProcess`, de-duplicated against agents and scripts). Otherwise the workspace closes directly, even when it has terminals. Confirming kills every terminal and discards any unsaved buffer without per-tab prompts, so the flow does not go through `closeTabs`. A hibernated workspace has no mounted editors, so its dialog lists the unsaved documents without Save buttons. When a Save fails (file changed on disk, file deleted, write error) the row shows the reason and offers "Go to tab", which closes the dialog and focuses the tab where the conflict overlay or the deleted-file screen already lives; while closing it also offers "Discard". The confirm button stays disabled until every failed document is fixed or discarded (`isBlockedByFailures`); hibernating has no Discard, so it requires the fix. `useDocument.save()` refuses to write a deleted file (`DELETED_SAVE_ERROR`); only `recreate` does. On unmount, an editor whose final autosave write fails, whose file was deleted or that is in conflict carries its buffer in memory (`unflushedBuffers`, process lifetime only) so hibernating does not lose it while Kex stays open. Hibernating on request saves every dirty document of the workspace first (`saveWorkspaceDocs`) whatever the `editorAutoSave` preference says, so the in-memory carry is only a fallback for a save that failed, and that document opens the dialog. The `warnOnCloseTabWithRunningProcess` preference no longer affects this path; it only governs closing a single terminal tab. Closing the last workspace quits the app. Panes inside a split still collapse when their last tab is closed - only the sole pane of a workspace stays empty.

**Native PTY via `portable-pty`.** Not a wrapper around `script` or `expect`. Kex spawns a real pseudo-terminal, so TUI apps (vim, htop, tmux, lazygit, etc.) work correctly, including mouse input and true color.

**Shell integration.** Kex injects init scripts at shell startup that emit OSC 7 (current working directory) and OSC 133 sequences (prompt boundaries, command start, command end, exit code). This enables:
- The file explorer to follow the active terminal's working directory.
- The optional **block terminal** mode (a panel with `blocks: true`): command output is grouped into blocks with per-block chrome (cwd, time, duration, exit badge on failure) and a hover toolbar (`Run again`, copy command/output, find in block). The shell's prompt is suppressed and input is driven by a host-rendered `ShellInput`. `Cmd+Up`/`Cmd+Down` navigate between command blocks.

Supported shells: zsh (full), bash (full), fish (full), PowerShell 7+ (full), PowerShell 5.1 (full), cmd.exe (no integration - basic terminal only).

**Split panes.** Terminals can be split horizontally and vertically within a pane. Each panel is an independent PTY. Splitting a pane creates a second pane alongside it; each pane has its own panel tab strip. Two limits apply, both configurable in `settings-general.json`: `paneSplitLimit` (default `{ width: 250, height: 250 }`) blocks horizontal splits when the pane is too narrow and vertical splits when it is too short; `workspacePaneLimit` (default `8`) caps the total number of panes per workspace. Both keyboard shortcuts and drag-and-drop zones enforce these limits, and the command palette disables its split rows at the same `workspacePaneLimit`.

**Inline search.** `Cmd+F` / `Ctrl+F` opens an inline search bar that searches the xterm.js buffer. Matches are highlighted in the viewport and you can jump between them.

**Link detection.** URLs in terminal output are clickable and open in the system browser.

**Scratchpad bar.** A per-terminal input bar (`terminal.scratchpad`, default `Cmd+U`) to compose multi-line text and send it to the shell without typing at the prompt, with drag-and-drop of explorer paths and an Enter / Shift+Enter send-mode preference. Its state is a single binary flag, `scratchpadOpen`: existence and focus are the same thing, there is no "open but unfocused" state. See [SCRATCHPAD.md](SCRATCHPAD.md) for the full model, and every focus/close path. It only ever appears when its shortcut is pressed.

**True color and 256-color.** The xterm.js WebGL renderer supports the full color space. The terminal color palette is driven by the active app theme, not hardcoded.

**WSL as a first-class workspace (Windows only).** Each tab can be set to run inside a specific WSL distro. The file explorer, git operations, and AI tools all operate inside that distro's filesystem - it is not a wrapped subprocess.

### 3.2 Code editor

**CodeMirror 6.** A proper code editor, not a textarea. Syntax highlighting, bracket matching, line numbers, code folding, multi-cursor, and tab/indent handling work correctly.

**Language support.** TypeScript / JavaScript (JSX/TSX), Rust, Python, Go, HTML, CSS, JSON, Markdown, PHP, C/C++/Java/C# (via legacy modes), and more. Language is detected from the file extension and the appropriate language pack is loaded on demand.

**Ten built-in editor themes**, independent from the app theme: Atom One Dark, Aura, Copilot, GitHub Dark, GitHub Light, Gruvbox Dark, Nord, Tokyo Night, Xcode Dark, Xcode Light.

**File sync.** The editor reads and writes files through the Rust filesystem commands. If a file changes on disk while you have it open (e.g., `git checkout`), the editor can detect the change via the file watcher.

### 3.3 File explorer

**Tree view with icons.** The Catppuccin icon theme covers the full range of file types. Folder icons are context-aware (e.g., `src/`, `.github/`, `node_modules/`).

**Keyboard navigation.** Arrow keys to move, `Enter` to open, `F2` / double-click to rename inline, right-click or context menu key for actions (new file, new folder, rename, delete, copy path, reveal in finder, open in terminal).

**Fuzzy search.** The search bar in the explorer panel searches file names under the active explorer root using the `nucleo-matcher` crate on the Rust side. Because the finder is scoped to the current root, it never surfaces files outside the view, and each result's path is shown relative to that root.

**Root modes (per workspace).** The explorer root is chosen by an explicit mode stored per workspace (`explorerRootMode` in the workspace body file `workspaces/<id>.json`) and selected from the dropdown above the tree. The "show hidden files" toggle (`showHidden`) is likewise per workspace and lives in the same body file (it was previously a global preference). The mode is the single source of truth for the root, whether a terminal or an editor pane is focused. The two modes:

In every mode the tree is prefixed by a non-collapsible header row showing the current root's full path (left-truncated when long, so the tail stays visible). The selector trigger shows the active mode's label (not the folder name) and its icon; each option's subtitle is its resolved path.

- **File System**: root starts at the user's home directory and is navigable per workspace (`fsRoot` field in the workspace body file `workspaces/<id>.json`, default home). Double-clicking a folder enters it (sets `fsRoot`). On top of the shared header, File System adds a `..` folder-style entry (shown only when not at the filesystem or drive root) whose double-click climbs to the parent directory; the selector uses the hierarchy icon. The `..` row exists only in this mode; Workspace Root is unaffected and double-click does nothing. If the current root is deleted from under the explorer, it silently relocates to the nearest existing ancestor (climbing the path and `fs_stat`-ing each candidate) instead of showing an error state. On a root change the open folders are carried over through the same rule used to restore a workspace snapshot (`carryOverExpanded`): folders under the new root stay open, going up also opens the old root, and an unrelated root keeps nothing; there is no per-root memory, so what a move down dropped does not come back.
- **Workspace Root**: root is a folder fixed via the "Set as workspace root" folder context action (stored as `workspaceRoot` in the workspace body file `workspaces/<id>.json`). The selector disables this option (showing "Set a new workspace root in the explorer" or "Folder not found") when no folder is set or the saved one no longer exists. If the folder is deleted while it is being shown, the explorer falls back to an informational empty state instead of a raw filesystem error.

The selection logic is the pure `resolveExplorerRoot` (`modules/workspaces/lib/explorerRoot.ts`, tested). The previous per-editor root override was removed: opening a file no longer changes the explorer root.

**Sidebar-driving panel (autofocus).** One panel at a time drives both the Explorer root and the Source Control / Git History repo. Anchoring happens via two explicit gestures only -- never automatically on every focus change or cwd update:

- **F4** (`tab.focusOnExplorer`) always anchors: it applies the cascade (see below), opens the sidebar if closed, and switches away from Git History to Explorer if needed (it stays on Explorer or Source Control otherwise).
- **Per-panel autofocus flag** -- toggled from the tab right-click context menu (crosshair icon shown on the tab when active). When an autofocus panel gains focus (or, for a terminal, its cwd changes while focused), it anchors silently: the same cascade runs, but the panel is never opened and the active sidebar tab is never changed.

Autofocus is **data-driven**, not an enumerated kind list: `isAutofocusTab` (`lib/types.ts`) is true for any panel that resolves to a filesystem location -- the terminal cwd, or any kind carrying a `path` (editor, markdown, git-diff, git-commit-file). Only `browser` (a web URL) and `git-history` (a commit list, no single file) lack it, so a future path-bearing panel kind opts in automatically with no code change. **Lock** (prevent close) is independent and applies to **every** panel kind with no exception. Both flags live on a shared `TabCommon` base, and the markdown/editor view toggle preserves them across the conversion.

The shared cascade (`resolveSidebarTarget`, tested): given the panel's reference path (a terminal's folder or an editor / git-diff file), if the workspace root **itself belongs to a git repo** (`workspaceGitRoot`) and a *different* git repo nested strictly inside the workspace root owns that path, it sets File System rooted at the nested repo (so a worktree or sub-repo under a project workspace is shown, not the parent). This re-root is gated on the workspace root being a repo on purpose: a non-repo container workspace (e.g. `~/Work` holding several independent project repos) stays in Workspace Root mode when you focus a file inside one of its projects, so navigating never drops the wider view. Otherwise: if the path is under the workspace root it sets Workspace Root mode; else if it is under a git repo it sets File System rooted at the git root; else it sets File System rooted at the common ancestor of the current fs root and the path (falling back to `dirname`). The nested git repo is resolved from the focused path via `git_resolve_repo` (which accepts a file path, resolving from its parent directory, so editor tabs anchor too); the workspace root's own repo is resolved once per root in `App.tsx` and passed in as `workspaceGitRoot`, not recomputed on every focus. Source Control and Git History resolve their repo from the resulting explorer root (`useSourceControl`); that resolution is keyed on the exact context path (`canReuseResolvedRepo`, tested), never on a path prefix, so anchoring into a nested repo/worktree re-resolves to it instead of reusing the parent. The `autofocus` flag is persisted per panel in `workspace-state.json`. The global `autofocusMode` preference (Settings > General: `manual` or `always`) decides how the flag is used: in `manual` the boolean `autofocusNewTabs` (a checkbox shown only in that mode) seeds the flag on tabs created from then on, and `always` makes every capable tab drive the sidebar (`isAutofocusActive`) while hiding the per-tab toggle, the tab crosshair and the explorer focus button; the stored flags are left untouched so they apply again when the mode is switched back. New-workspace terminals default to no autofocus; when no autofocus panel exists the sidebar root and git repo stay wherever they were last anchored.

**Focus on Explorer.** A tab context-menu action and `F4` shortcut reveals the tab's file (editor / markdown / git-diff / git-commit-file) or, for terminal tabs, its current folder, in the tree. If the active view already contains the target it is just expanded and selected; otherwise the explorer switches to File System rooted at the deepest common ancestor of the reference fs root and the target (falling back to the target's parent dir when there is none). Unlike the removed automatic per-editor override, this is an explicit user action. The decision is the pure `resolveFocusTarget` (same file, tested); revealing is driven by a `revealRequest` prop on `FileExplorer` that re-runs as the tree reloads asynchronously, expanding each ancestor until the target loads, then selecting and scrolling to it without taking focus from the editor. A reveal triggered from a path-bar click or shortcut opens the sidebar if it is closed and switches to Explorer from **any** other view (Git or History), not just History. `applyRevealTarget` holds the reveal (`"pending"`, no consume) until the explorer is the active/visible tab and re-runs once it is, so the select-and-scroll lands on the first request instead of firing off-screen while the panel is opening or on another tab. Switching the active tab no longer selects that tab's file in the explorer (the old `activeFilePath` sync was removed); selection happens only on an explicit reveal. A reveal skips its flash when the target is already the selected row, so opening an already-open file from the sidebar (which selects it on click) does not produce a circular flash.

**Sidebar view state per workspace.** `Workspace.sidebar` (`sidebarSnapshot.ts`) holds `{ view, expanded, selectedPath, scroll }`: the active view, the open explorer folders, the selected row and the scroll offset tagged with the root it was measured on. It rides in the workspace body, sanitized by `sanitizeWorkspaceSidebar`. Only `open`, `side` and `width` stay per window. The explorer is remounted per workspace (`key` in `Sidebar.tsx`) and applies the snapshot only at mount, through the pure `restoreExplorerSnapshot(snapshot, root)`: it keeps the paths under the current root (`isUnder`), adds their intermediate folders so every open folder is reachable, and restores the scroll only when it was recorded on that same root. A root change inside a session carries the open folders over through the same rule (`carryOverExpanded`, which also opens the previous root), with no per-root memory. A restored selection whose row is missing is kept while any folder from the root down to its parent is still loading (`shouldClearSelection` with `ancestorListingPending`, `staleSelection.ts`), because the restored folders are fetched at once and finish in any order. A restored scroll offset waits until the list is tall enough; once no listing is loading it is clamped to what fits (`resolvePendingScroll`, `pendingScroll.ts`), and wheel, pointer or keyboard input in the explorer, a reveal or a root change drops it, so it never stays armed. A `revealRequest` (`revealRequest.ts`) carries the workspace it was issued for and a nonce: the Sidebar drops a request for another workspace, and a freshly mounted explorer treats the nonce present at mount as already consumed, so returning to a workspace never replays the last F4 or autofocus reveal over the restored state. Changes are reported through a coalescer with a 10 s window (`sidebarSnapshotSync.ts`, built on `createCoalescer`): the first change after a quiet window is saved at once, later ones wait for the rest of the window and go out together, and then follow the normal debounced workspace save. A snapshot equal to the stored one, which is what most mounts report, changes nothing (`applyExplorerSnapshots`). The pending batch is flushed synchronously before opening, closing or moving the Sidebar (`withSidebarSnapshotFlush`, so the flush and the remount land in one render), after a workspace switch, before hibernating, on `beforeunload` and on window close or quit (`main.tsx`), so a restore never reads a stale snapshot. No flush is needed for moving a workspace to another window because that action does not exist: a workspace belongs to one window for its whole life, and a feature that adds the move must flush first. A stored `notes` view on a workspace without a root is shown and handled as Explorer everywhere (`effectiveSidebarView`). A workspace switch or a wake does not itself trigger the autofocus reveal (`autofocusDecision`), otherwise the reveal would overwrite what was just restored; a later change inside that workspace does, such as focusing another tab or an agent in the focused tab reporting the worktree it entered.

**Attention flash.** A shared `FlashOverlay` (`src/components/FlashOverlay.tsx`) renders a `key`-remounted overlay span that pulses the primary color over its `relative` parent; bumping the `key` token replays the CSS animation (`terax-flash`, `styles/globals.css`) with no effects, rAF or className mutation, so it survives React strict-mode double-mounts and virtualizer re-renders. Two variants: `fill` (tints the element) and `ring` (outlines the border, reusing the center drop indicator's `ring-2 ring-inset ring-primary/60 rounded-md`). Used by: the revealed explorer row (fill), the explorer root row when a focus re-roots the tree (fill), the locked-tab lock icon on a blocked Cmd+W (fill, `lockFlashStore`), and the whole pane border when activating an already-open file's tab (ring, `tabFlashStore`, isolated in `PaneFlashBorder` so the memoized `PaneView` is not re-rendered). The animation is a single pulse and is intentionally kept under `prefers-reduced-motion` since it animates opacity only.

**Drag to open.** Files (not directories) can be dragged from the explorer and dropped onto any pane drop zone or between tabs to open them as permanent editor tabs. Dropping on a directional zone (top/bottom/left/right) splits the target pane and opens the file in the new sub-pane. The drag experience is visually identical to dragging tabs between panes. See `WorkspaceDndProvider.tsx`.

**Drag to move.** Dragging a file or folder onto another folder row moves it there (`fs_rename`). Built on the same `@dnd-kit` context as drag-to-open (not a second pointer system): folder rows are `useDroppable` (`explorer-dir:<path>`), folders drag as `dir:<path>` (move only, ignored by the pane-open handler), files as `file:<path>` (openable in a pane *and* movable). The move is committed by `useDndMonitor` in `FileExplorer` calling `tree.movePath`; the drop target is only registered for valid destinations (not self, current parent, or a descendant) and `movePath` additionally refuses name clashes. Hovering a collapsed folder for 700ms springs it open.

**Drop files from the OS.** Dragging files/folders from Finder/Explorer onto an explorer folder copies them in (`fs_copy`, recursive, refuses to overwrite). Uses Tauri's native drag-drop (`onDragDropEvent`), one webview listener that hit-tests by `data-fs-path` / `data-explorer-drop`. It coexists with the terminal's own OS-drop listener (`useTerminalFileDrop`, which hit-tests `data-pane-leaf`): both receive every event but each acts only on its own DOM region, so they never steal each other's drops.

**Add to .gitignore.** A file/folder context action, shown only inside a git repo (`gitRootPath != null`). It appends an anchored entry (`/<relPath>`, trailing slash for folders) to the repo-root `.gitignore`, idempotently. The non-obvious part is collision with an already-open editor: if `.gitignore` is open in a panel, the buffer is the source of truth, so the line is inserted into the CodeMirror buffer (`EditorPaneHandle.insertAtEnd`) and the tab goes dirty like any edit, never touching disk (so unsaved edits are never clobbered and autosave is irrelevant); otherwise it reads/appends/writes on disk and reveals the file. Pure logic in `modules/explorer/lib/gitignore.ts` (tested); orchestrated in `App.tsx` (`handleAddToGitignore`).

**Git decorations.** Optional (Settings > General > Explorer, **off by default**). Tints each file name by git status (modified/added/deleted/renamed/untracked) and dims gitignored entries; collapsed folders bubble up the highest-priority status of their children. The data rides the always-resident Source Control snapshot (no extra git IPC or watcher); the only backend cost is a `max_depth(1)` `WalkBuilder` per directory read, and only when the flag is on (gated to a real git repo so it never trips macOS folder-access prompts outside one). Pure logic in `lib/gitStatusUtils.ts` (tested); colors in `lib/gitStatusColor.ts`.

### 3.4 Source control

**Git status and staging.** The source control panel shows modified, staged, untracked, and conflicted files. You can stage / unstage individual files. The diff view uses the CodeMirror merge extension. Git diffs render unified (inline `unifiedMergeView`) or split (side-by-side `MergeView`), controlled by the global `diffViewMode` preference (Settings -> Editor). Split mode mounts a `MergeView` class outside the `<CodeMirror>` wrapper because it is not an extension. Wrap and line numbers in diffs reuse the per-extension `editorViewByExt` config, edited from the diff bar's `[...]` dropdown.

**Commit.** Type a commit message and commit with `Cmd+Enter` / `Ctrl+Enter`. No separate terminal command needed. A **Push** checkbox next to the Commit button, when checked, pushes to the remote right after a successful commit (the button label switches to "Commit & Push"). Both the draft commit message and the Push flag are git settings stored **per workspace** under the `git` section of `workspaces/<id>.json` (`{ commitMessage, pushOnCommit }`), so each workspace keeps its own in-progress message. The message edits live in panel-local state and are persisted to the workspace on a short debounce (and flushed on workspace switch and after a successful commit) to avoid re-rendering the app on every keystroke.

**Push.** Push to the remote with upstream awareness - Kex tells you if you are ahead, behind, or diverged before you push.

**Branch display.** The current branch (or detached HEAD state) is shown in the header.

**All git operations are gated on workspace authorization.** A directory must be authorized (see section 4.2) before any git command can run against it. This prevents the source control panel from operating on paths that were not explicitly opened.

### 3.5 Git history

**Commit graph.** The git history pane renders a proper commit graph with lane routing for merges and branches, similar to GitLens or Sourcetree. Refs (branches, tags, HEAD) are shown on the relevant commits.

**Per-commit diffs.** Click a commit to see its changed files. Click a file to see the full diff for that file in that commit.

**Remote links.** For commits on GitHub/GitLab/Bitbucket remotes, there is a link to open the commit page in the browser.

**Commit search and filter.** Filter the history by commit message, author, or date range.

### 3.6 Terminal coding-agent notifications

When Claude Code (or a future compatible agent) runs inside a Kex terminal, Kex detects its state through two channels: OSC 133 C (shell integration, always active) and a per-session Unix domain socket for Claude Code hook events. The tab shows a spinner while the agent is working (every spinner in the app is the single `Spinner` of `components/ui/spinner.tsx`, in `text-primary`; Settings > Appearance > Spinner picks its look through the `spinnerStyle` preference: `arc`, `braille` or `cursor`), an amber dot when it needs your input, and no indicator when it is idle. Background subagents count as work: each session keeps a `subagents` record (filled by `SubagentStart`/`SubagentStop` and corrected from the `background_tasks` of every `Stop`), a `Stop` with any subagent alive leaves the session `working` (`lib/subagentGate.ts::stopOutcome`), and the amber dot appears with the `Stop` of the turn Claude opens when the last subagent finishes. A notification bell in the header lists active sessions and recent events with OS notifications when you are away from the window.

The indicator is cleared by any of: the agent's `Stop` hook firing normally, the agent process exiting (OSC 133;D), the PTY closing, or the user typing anything in the terminal. The last condition ensures the indicator never lingers after Ctrl+C or abnormal termination.

The Unix socket (`kex-ipc-{pid}-{pty_id}.sock`, path in `KEX_IPC`; the Kex process pid in the name keeps the installed and dev instances, which share the directory and both number PTYs from 1, from stealing each other's socket; sockets of dead pids are swept the first time a path is built) is created before the child process starts in `session::spawn()` and cleaned up on PTY close. It lives under `XDG_RUNTIME_DIR` when available, otherwise under an owner-only (0700) per-uid directory Kex creates itself in the system temp dir rather than directly in that shared, world-writable location, and the socket file itself is forced to 0600, so another local user cannot pre-create the path or connect to it. Claude Code hooks send raw JSON payloads to it; `pty/ipc.rs` dispatches them to Tauri events consumed by the frontend.

**Notification bell scoping.** Each main window runs its own React runtime with its own Zustand store. `kex:agent-signal` is broadcast globally, but `leafIdForPty()` is window-local, so each window's `AgentNotificationsBridge` only processes signals from PTYs that belong to it. The bell in each window shows only that window's agents.

**OS notification deep-link.** When the app is unfocused the frontend calls `agent_os_notify` with `{ windowLabel, workspaceId, tabId, title, body }`. On macOS Rust sends the notification with `mac-notification-sys` on its own thread and waits for the response; only a direct click on the notification focuses the window and emits `kex:activate-tab`, which `onActivateAgent` handles (switch workspace, activate tab, focus the terminal after 50 ms). Focusing the app any other way (clicking its window, Cmd+Tab) never navigates. Other platforms send the notification through `tauri-plugin-notification`, with no click navigation. In `pnpm tauri dev` the notification is delivered as Terminal.app (the plugin does the same), so clicking it does not reach Kex: test the click on an installed build.

**Agents in the WorkspaceBar.** In the wide bar (above 80px) each workspace shows, after its name, a dimmed count of its active agents (working, waiting or in error; `buildAgentEntries` already derives them, idle agents do not count), whatever the setting. One box in Settings > Workspaces decides what the expand arrow of each workspace lists (everything by default); with nothing included (`hasDetail` false) there is no arrow and the count is all the bar adds. `workspaceDetailTerminalsEnabled` ("Include terminals") turns terminals on, and nested under it `workspaceDetailTerminals` (`all`, `agents`, `active-agents`) picks which ones; `useDetailFilter` folds both into `DetailFilter.terminals`, where `none` means terminals off. Three independent checkboxes add other kinds: `workspaceDetailEditors` (editor and markdown tabs), `workspaceDetailBrowsers` and `workspaceDetailGit` (git-diff, git-history, git-commit-file). The arrow state is per workspace (`Workspace.detailExpanded`, persisted with the workspace body). `workspaceDetailRows` (`workspaces/lib/workspaceDetail.ts`) is the pure selection: tab order, except with `active-agents`, where the agents come first in the urgency order of the entries and the other included tabs follow. Each nested row (`WorkspaceDetailList.tsx`) reuses `useAgentTabTitle`, so its title is the one the tab bar shows; rows always start with an icon (the agent icon for agents, the tab bar icon for the rest) and end with a spinner (working), an amber dot (waiting) or a red dot (error). In the active workspace only, the row of its focused tab (`focusedTabId` of the active pane) gets a stronger background, full-color text and `aria-current`. Clicking a row goes through `onActivateAgent`, like the bell. Right-clicking a row opens the same menu as the pane tab (`TabContextMenuItems`), without the New Terminal / New Browser entries. The row does not know its pane, so `SidebarTabMenuContext` hands it one never-changing object (it reads the latest workspaces through refs, which keeps the memoized list from re-rendering) keyed by tab id: Close Other Tabs and Close All Tabs resolve the pane that holds the tab in the `paneTree` and close its tabs through the same close queue and the same `isBulkClosable` rule as the pane menu (`bulkClosableIds` / `otherBulkClosableIds`). Rename from a row starts the rename with origin `sidebar`, so the field opens anchored to the row (`TabRenamePopover`) instead of on a pane tab that may be hidden. Each row menu is also closed by `contextMenuCloseStore`, like the workspace menus, when the `tab.rename` shortcut starts a rename. A row whose tab has background subagents (`AgentSession.subagents`, see the agents notes above) is followed by one child row per subagent (`SubagentRow`, ordered by start time through the pure `subagentRows`): grouped under a thin vertical line like the tab rows of a workspace, each with the agent icon of the parent tab, labelled with the subagent description or, without one, its agent type (or "subagent" when neither is known), with a spinner at the end. When the parent tab is focused, its focus chip wraps the row and its child rows together. Child rows read the `sessions` the list already subscribes to, are plain non-interactive rows (no hover surface, no click, no drag, no close button or menu): the hover surface belongs to a wrapper around the tab row and its child rows, so hovering any of them highlights the whole block. They appear and disappear with the `subagents` record, with no setting of their own and no effect on the active-agent count, which counts tabs. Claude Code sends no hook when Ctrl+C pauses the subagents (they stay resumable by writing to them, which sends a new `SubagentStart` with the same id), and Kex deliberately does not read that keypress, so paused subagents keep their row and spinner until the next `Stop` reconciles them through `background_tasks`. An empty list renders nothing. The compact bar shows neither the count nor the list.

### 3.7a Agent session restore

When an agent session is running at the time Kex closes, Kex offers to resume it automatically on the next launch. The tab showing a restored session displays `agentname · dirname` as its title, a `✦` icon, and a status indicator (spinner while working, amber dot while waiting for input, nothing when idle). If the resume command fails (missing transcript, deleted directory), the icon becomes `⚠` and the title turns red.

Hooks must be installed via "Set up Claude Code" (notification bell popover) for this feature to work. All per-agent session knowledge (transcript source, cwd read-back, resume templates, missing-transcript policy, stripping whitelists) lives in one `Provider` table (`src-tauri/src/modules/agent/provider.rs`; `claude`, `codex`, `opencode` and `omp` today), and `session_store.rs` consults it instead of hardcoding agents. See `docs/AGENT_SESSION_RESTORE.md` for the complete design and edge cases.

**OpenCode.** It has no hook commands, so its integration ships as a plugin script Kex writes into `~/.config/opencode/plugins/` (`agent_setup_opencode`, bell popover, "Install OpenCode integration"): the plugin translates the session lifecycle (`session.created`/first busy event into `SessionStart`, `session.status` busy into `UserPromptSubmit`, idle into `Stop`, `permission.asked`/`question.asked` into `PermissionRequest`, `session.error` into `StopFailure`) into frames with `agent: opencode` on the per-terminal socket. A session resumed via `--session` fires no `session.created` (anomalyco/opencode#39711), so the plugin registers a session on the first event that names it, and asks the OpenCode client for its parent once so a resumed subagent is never mistaken for the tab's session. Its provider row has no transcript source (OpenCode keeps sessions in a SQLite database Kex does not touch, so the tab menu block offers "Copy Session ID" but no transcript) and its `--session <id>` resume; the row never prunes records.

**OMP.** Its extension API (shared with Pi) is TypeScript files its own process loads from `~/.omp/agent/extensions/`: Kex writes `kex-agent-status.ts` there (`agent_setup_omp`), which translates the runtime's lifecycle events into the same hook-event frames. Its provider row scans `~/.omp/agent/sessions` for `<timestamp>_<id>.jsonl` files, reads the cwd from the `session` header (JSONL line 2) and resumes with `omp --resume '<id>'`. Frames are gated on the per-terminal `KEX_IPC`/`KEX_TAB_ID` env vars, so a bare `omp` run is untouched. **Pi** reuses the same extension source (stamped with `agent: pi` by `agent_setup_pi`, installed in `~/.pi/agent/extensions/`), has its own provider row scanning `~/.pi/agent/sessions` (header on JSONL line 1, `CwdRead::HeaderLine(1)`) and resumes with `pi --session '<id>'`; a Pi session without any turn writes no file and records nothing. Pi ends a turn on `agent_settled` only (it keeps working after `agent_end`), and the OMP and Pi status commands compare the whole installed file with the script stamped for that runtime.

### 3.7 Web preview

**Auto-detected dev server.** When a localhost URL is detected in the terminal output (e.g., `http://localhost:5173`), a pill appears in the status bar offering to open a preview tab. The preview tab renders the URL in a native child webview - not an iframe inside the main webview.

**Image and PDF viewers.** The preview pane also handles images and PDFs opened from the file explorer.

**Sandboxed.** The preview runs in its own webview context. It cannot communicate with the Kex app surface.

### 3.8 Themes and customization

**App theme.** The theme engine writes CSS custom properties to the document root. All UI components consume the theme through those variables. There are 10 built-in app themes: Kex Default, Nord, Tide, Catppuccin, Tokyo Night, Caffeine, Claude, Gruvbox, Sage, Rose Pine.

**Faithful palettes, readable text.** The palette files of the built-in themes keep the original values of the project they come from (Kanagawa, Everforest, Nord, ...). `themes/index.ts` runs `withReadableTheme` (`readableColors.ts`) over the built-in ones when registering them: it nudges text, `destructive`, the focus indicator, the derived `link` token, the terminal text and the darkest/lightest ANSI colors toward black or white, as little as needed, to reach their contrast floor (floors and exceptions in `docs/THEMES.md`). Editor syntax themes get the same treatment (`readableSyntax.ts`). Themes created by the user are applied untouched. The unselected workspace chip in the WorkspaceBar is a translucent `foreground` overlay rather than `muted`, so it stays visible in every palette; a selected, colored workspace carries white text while collapsed (expanded, its chip keeps only a border in its color and the focused tab row takes the fill), and `chipColorOnWhite` (`workspaces/lib/workspaceColor.ts`) darkens its color just enough for white to reach 4.5:1, keeping the hue.

**Theme editor.** You can create and edit themes in-app. Changes are live-previewed. Custom themes are persisted to the settings store and can be exported as JSON files to share.

**Editor and terminal surfaces have their own colors.** A theme variant may carry `editor: { background, foreground }`, written by `applyTheme` as `--editor-background` and `--editor-foreground` (defaults in `globals.css` fall back to `--background` and `--foreground`, so themes without it look as before). The CodeMirror editors (code, markdown Source and Rich), the markdown preview and the editor path bar paint `--editor-background`; the terminal pane and its path bar paint `--terminal-background`. `resolveEditorSurface` (`modules/theme/resolveEditorSurface.ts`, pure) picks the surface: with the editor theme on Auto it is the app theme's own `editor`; with an explicit editor theme it is that CodeMirror theme's own background and text color, read once from a hidden view (`editor/lib/editorThemeSurface.ts`, loaded lazily only when the preference is explicit). The Settings sample follows the same rule. A borrowed terminal palette whose theme leaves out background, foreground, cursor, cursor accent or selection takes them from that theme's own UI colors and, if the variant defines none either, from fixed values of the variant's own mode (`MODE_DEFAULTS` in `resolveTerminalTheme.ts`), never from the active app theme: a dark palette lent to light mode keeps light text and cursor.

**Light terminals lift low-contrast colors.** xterm runs with `minimumContrastRatio` 4.5 in light mode and 1 in dark (`minimumContrastRatioFor`, `styles/terminalTheme.ts`), applied when a terminal is created and again on every theme or mode change. Programs choose colors for a dark terminal (white, light yellow), which are unreadable on a light background; dark mode keeps the palette exactly as the theme defines it.

**Terminal theme is independent.** The `terminalTheme` preference (`settings-general.json`) is `"auto"` (default: the active app theme's own terminal palette) or the id of any built-in or custom app theme (optionally pinned to a mode as `id@dark` or `id@light`, so a dark palette can run under a light app theme; `parseTerminalPref`/`formatTerminalPref`), whose terminal palette (16 ANSI, background, foreground, cursor, selection) is borrowed without duplicating its values. `resolveTerminalPalette` (`modules/theme/resolveTerminalTheme.ts`, pure) picks the palette and falls back to the app theme's when the id is unknown or that theme has no palette at all; every built-in theme defines its own terminal palette (16 ANSI colors) and a paired editor theme in both modes, with the same brightness as the mode, locked by `themes/themes.test.ts`; only a user theme with a palette in a single mode lends it to the other mode; `ThemeProvider` passes the result to `applyTheme`, which writes the `--terminal-*` variables, so only the terminal changes. `inactivePaneDim` still comes from the app theme (it is a black overlay, independent of the terminal background). Settings > Themes is one table (`settings/components/ThemeTable.tsx`): a row per app theme with three columns, theme, editor and terminal, and a single Auto checkbox in the Theme header. Auto is the `themeAuto` preference (default on, `settings-general.json`): while it is on, picking another app theme resets the editor and terminal preferences to `auto`, so they follow it; the editor and terminal cells stay clickable either way and picking one never turns Auto off, it only holds until the next app theme change. Turning Auto on resets both to `auto` at once. A selected cell gets an outline, and adjacent selected cells of a row join into one outline. Three fixed previews (interface, editor, terminal) sit above the rows, and an eye icon on each editor or terminal cell opens a larger preview (a lazy read-only CodeMirror sample for the editor) in a popover. What each theme uses, and whether another theme shares it, comes from the pure `themeSurfaceInfo` (`modules/theme/themeSurfaceInfo.ts`); A theme that has a different editor theme or terminal palette in each mode (`surfaceModes`) shows a sun or moon button next to the eye of that cell to view and pick the variant of the other mode, which is how a dark editor or terminal is used under a light app theme. The button exists only on the selected cell, which always shows the variant it is really using; every other cell always shows the variant of the app mode, so selecting another cell, or changing the app mode, puts the rest back in line without changing what is selected. `unpairedEditorThemes` lists the editor themes no app theme pairs in any mode, shown as "Editor only" rows in both modes so they stay selectable. Terminal palettes that are not an app theme live in `listTerminalOnlyThemes()` (`themes/index.ts`, kept out of the built-in list so they never appear as app themes; today `ghostty-default-style`, Ghostty's Default Style Dark plus a light variant derived from it, locked by `themes/themes.test.ts`): `ThemeProvider`, `ThemeTable` and the preview page add them to the terminal catalog, and the table lists them under "Terminal only" with the same mode toggle. Known limitation: xterm's minimum contrast still follows the app mode, not the pinned palette (TASK-785).

**Editor theme is independent.** The editor theme is a separate setting from the app theme. You can have a Catppuccin app theme with a GitHub Light editor theme.

**Terminal palette follows app theme.** The xterm.js ANSI color palette (colors 0-15) is derived from the active app theme, so the terminal colors are consistent with the UI.

### 3.9 Command palette

`Cmd+K` / `Ctrl+K` opens the command palette. It supports multiple modes (file finder, command runner, content search) distinguished by a prefix character. Fuzzy matching. Results are ranked by recency (MRU). Every row starts with a tag saying what choosing it does (`RowTag`: Tab, Workspace, Action, Setting, Folder, File), so a tab, a workspace, an action and a closed location no longer read alike. A tab row is up to four lines: the title, the absolute path the tab points at (`tabLocation`, `command-palette/lib/rowDetail.ts`: the cwd of a terminal, the file of an editor, the url of a browser) the process and the branch (`tabDetailLines`: the name of the process the terminal runs, without arguments, unless an agent is in it, and the branch; together they take a line of their own, `top · main`, and alone they join the path, the process before it and the branch after it) and the note, collapsed to one line, when it has one; there is no side panel, the note lives in the row. The leading icon is the same as the pane tab strip (`TabBarIcon` in `workspaces/lib/tabBarIcon.tsx`, shared by `PaneTabBar` so the two cannot drift) and the trailing mark is the workspace the tab belongs to, drawn with `WorkspaceMark` (its icon in its color, or its color dot) plus its title, resolved like the WorkspaceBar resolves it. Action rows sit under a heading named `<group> actions`, so a group never reads as a row kind. The dialog is `min(720px, 100vw - 32px)` wide and hangs from a fixed top edge (the `CommandDialog` default, one third down the window), so the input does not move when the list shrinks. In `mergeRows` a tab found by process, branch, worktree, location or workspace name ranks above any action whose letters only match scattered (`Toggle full pane` for `top`); an action that starts a word with the typed text still ranks above them.

Closed terminals and files (`closedEntries.ts`, backed by `tab-history.json` through `tab_history_*`) enter the same list, tagged Folder or File, under "Recently closed" when the box is empty and ranked with the live rows while typing. They are hidden while their location is open again and deduplicated by kind and path. `uses` counts every focus of a tab at that location, whether it was opened from the explorer, from the palette or simply returned to; the counter adds one tier per use in `mergeRows`, so a folder returned to twenty times beats a live tab while a never-used entry stays below it. Reopening from the palette therefore counts through the resulting focus, not through a separate bump. Uses are batched in the frontend and flushed at most once every ten seconds, always before a tab closes, before the palette reads the list, and on window close or quit (`main.tsx`). Choosing one wakes its workspace if needed, opens a terminal in that folder or the file in an editor, and falls back to the active workspace with a toast when the original one no longer exists. Moving the active tab to another workspace opens a workspace subpage (like themes) with an explicit "New workspace" row and a sleeping mark on hibernated targets; Escape or Backspace on an empty box returns to the root list.

### 3.10 Settings

Settings open in a separate window (not a panel in the main window). Deep-linking is supported - `openSettingsWindow("shortcuts")` opens directly to the Shortcuts section. The settings window is `always_on_top` relative to the main window.

Navigation is a left vertical sidebar. Sections: General, Workspaces, Editor, Terminal, Appearance, Themes, Shortcuts, About. General holds tabs, explorer, agents, and startup; Workspaces holds workspace behavior such as auto-hibernate; Editor and Terminal each own their font, behavior, and cursor settings; Appearance holds zoom, the default tab and workspace title templates, and Git file colors; Themes holds the color mode, theme picker, and editor (syntax) theme. The sidebar dock side is no longer a global setting: it is per-window state (see below) flipped from each window's header toggle, since the standalone Settings window cannot target a specific main window.

**Workspace groups.** Workspaces can be organized into named groups in the WorkspaceBar. A group is `WorkspaceGroup { id, label }` (`modules/workspaces/lib/types.ts`, ids `grp-...` from `newGroupId()`) and a workspace joins one through its optional `groupId`. Groups belong to each window, not to the global preferences: `App.tsx` holds them in state and persists them through `window_save_groups` (`workspaceGroupsState.ts`, Rust `window_state`), and the collapsed ones through `window_save_collapsed_groups`. A group is created from a workspace (born with the label "Group"), can be renamed and reordered, and a group left with no members is pruned (`pruneEmptyGroups`). The sidebar order comes from the pure helpers in `modules/workspaces/lib/workspaceOrder.ts` (`groupWorkspaces`, `groupWorkspacesForDrag`, `visibleWorkspaceOrder`), the single source of truth for visual order, so navigation and rendering agree: workspaces with no valid group come first, then each non-empty group; while a drag is active every group is listed, even empty ones, so each is a drop target. A `groupId` that matches no group counts as no group. A new workspace (`addWorkspace`, via `insertWorkspaceAfterActive`) is inserted right after the active one in the state array and inherits its `groupId`.

**State granularity (global vs per-window vs per-workspace).** Three tiers:

- **Global preferences** (`settings-general.json`, shared by every window): fonts, cursors, themes, behavior toggles, etc. Edited from the Settings window and surfaced live via `onPreferencesChange`.
- **Per-window sidebar chrome**: whether the sidebar is `open`, its `width` (a react-resizable-panels percentage), and its `side` (`"left"` / `"right"`). Held as React state by `useSidebarState(label)` (`modules/workspaces/lib/useSidebarState.ts`), seeded from the restored `WindowEntry.sidebar` and persisted per window through the lightweight `window_save_sidebar` command (debounced, index-only write). It is a property of the window, shared by all of that window's workspace tabs. Validation/defaults live in `sidebarState.ts` (`open=true`, `width=20`, `side="left"`; an invalid `side` falls back to `"left"`; `width` clamped 12..70). The active view (`"explorer"` / `"git"` / `"history"` / `"notes"`) is not part of this state: it lives per workspace in `Workspace.sidebar.view`.
- **Per-workspace explorer state**: `explorerRootMode` / `fsRoot` and `showHidden` (show dot-files), each remembered per workspace because every workspace points at a different project. They ride inside the workspace body via the existing `saveWorkspaceState` / `sanitizeWorkspace` path; no dedicated IPC. `showHidden` moved here from a former global preference.

### 3.11 App detection

Kex finds the editors, IDEs and tools installed on the machine so that app Actions (see 3.12) can start from them. It is made of a Rust detection backend and a frontend catalog; the launch itself is `action_spawn` (see IPC.md), driven by an Action, not by this module.

**Catalog.** Both the Rust backend (`src-tauri/src/modules/editors/catalog.rs`) and the TypeScript frontend (`src/modules/external-editors/catalog.ts`) maintain a parallel list of known tools. Each entry carries:
- A stable `id` (used as the icon filename key and as `Action.appId`)
- A macOS bundle ID for `mdfind` detection
- A CLI binary name for `which`/`where` PATH lookup
- `args_before_path`: arguments injected between the binary and the target path at launch time
- `macos_app_name`: JetBrains `open -na <App>.app` fallback

The frontend catalog additionally carries `group` and `type` metadata: the target type (`"file"` for the VS Code family and text editors, `"workspace"` for JetBrains and Xcode) decides which variable an app suggestion ends with (`{filepath}` or `{workspace}`; JetBrains offers no file variant because its editors only open a workspace or a folder).

**Detection (Rust).** `detect_all()` in `detect.rs` iterates the catalog and resolves each entry per platform:
- **macOS**: `mdfind kMDItemCFBundleIdentifier == "<id>"` locates the `.app`; on failure, falls back to `which`. Resolution order: `open -b` for open-only editors (BBEdit, CotEditor, CodeRunner), Zed CLI inside the bundle, JetBrains Toolbox script or `open -na`, then general case (PATH binary with `args_before_path`, or `open -a`).
- **Linux/Windows**: Toolbox script or `which`/`where` binary lookup.
- The result is a `DetectedEditor` with the resolved binary and `args_before_path`. `runEditorScan` (`useExternalEditors.ts`) runs a scan at startup and from the Scan button of Settings > Actions, keeping the `enabled` flags the user set, and stores the result in `detectedEditors` (`settings-tools.json`).

**Suggestions and icons.** `appSuggestions.ts` turns the detected list into starting points for app Actions (name, icon, an editable command). `EditorIcon` (`src/modules/external-editors/EditorIcon.tsx`) tries `/assets/editors/<id>.svg`, then `.png`, then a generic document-code icon; `ActionIcon` picks it for any Action with an `appId`. Custom apps have no catalog entry and show the generic icon. There is no Header button and no editor-specific preference any more: which file or folder an app receives is whatever its command template says.

### 3.12 Actions

An **Action** is a saved command template that Kex runs against the current context. It replaced the former workspace Scripts, the Run button and the "Open in" external editor button; none of those exist any more, and nothing was migrated: old scripts and custom editors are simply gone. The type lives in `src/modules/actions/lib/types.ts`:

| Field | Meaning |
|---|---|
| `id` | `newActionId()`, prefix `ac-` |
| `name` | label shown in the Header and menus |
| `runInTerminal` | `true`: a script, typed into a terminal and stoppable. `false`: an app, spawned in the background, no stop |
| `command` | template, expanded at run time (variables such as `{cwd}`, `{workspace}`, `{filepath}`) |
| `appId` | detected app it came from, for its icon and default command |
| `cwdMode` / `cwd` | scripts only; `workspace` (default), `context` or `fixed`, with `cwd` only for `fixed` |
| `ownButton` | own split-button in the Header, or grouped in a shared menu |

**Two scopes, same shape.** Workspace Actions (`Workspace.actions`, with `Workspace.activeAction` for the one F12 runs) are saved with the rest of the workspace JSON and are meant for scripts (`npm run dev` belongs to a project). Global Actions (`Preferences.actions`, key `actions` in `settings-tools.json`, written by `setGlobalActions`) are meant for apps and are available in every workspace. Actions carry no tab id: which terminal a script runs in is runtime state, never persisted. A workspace saved by an older Kex may still hold `scripts` and `activeScript`: they belong to the removed Script model and nothing migrates them, so `sanitizeWorkspace` drops them when the workspace is read, and the next save writes the file without them. Those scripts are simply gone.

**Pure core** (`src/modules/actions/lib/actions.ts`, no I/O): `addAction` (ignores a repeated id), `updateAction` (never changes the id), `removeAction`, `reorderActions`, `normalizeActions`, `promoteToGlobal` and `partitionForHeader`. `normalizeActions` runs on every read from disk (`sanitizeWorkspace` for the workspace scope, `loadPreferences` and `setGlobalActions` for the global one): it trims, drops entries that are malformed, have an empty command or repeat an id, falls back to the id when the name is blank, and strips `cwdMode` / `cwd` from apps and `cwd` from any mode other than `fixed`. `addAction` and `updateAction` run the same normalization, so memory never differs from what is persisted: an add or update that would leave an empty command is refused and the list keeps its previous value. `promoteToGlobal` moves an Action out of the workspace list into the global list keeping its id, or giving it a fresh one when that id is already taken there (`adoptAction`), so neither version is lost. `partitionForHeader` splits a list into `ownButtons` (in the user's order) and the grouped `scripts` and `apps`, which the Header shows as two menus because only scripts have a stop control.

**Global list writes.** The preferences store only follows a write after it reaches disk and comes back as an event, so two quick changes would both start from the same stale list. `createGlobalActions` (`actions/lib/globalActions.ts`, bound to the preferences store in `globalActionsBinding.ts`) keeps a synchronous copy of the list while writes are in flight, serializes the writes (each one carries the latest list), and takes an Action back out and rejects when its write fails. The copy lives only while writes are in flight and until the preferences store reports any change after them (its echo or another window's edit), at which point the store is the truth again, so a later change never starts from a stale list.

**App suggestions** (`actions/lib/appSuggestions.ts`, pure). Apps enter Actions only through the add flow of the editor, so the detected list is turned into starting points: `suggestionsFromDetected(detected)` returns one `AppSuggestion { key, appId, name, iconId, defaultCommand }` per enabled app and preset variable, with keys `<id>:path`, `<id>:workspace` and `<id>:cwd` and names like `<Name> (workspace)`, and `CUSTOM_APP_SUGGESTION` is the blank one (empty command, generic icon). The default command is the binary plus the arguments `detect.rs` found, written as a template for the argv expander (an element with spaces or quotes is quoted, braces are doubled so a path never reads as a variable), ending in the preset variable; there is no per-app "best" target any more, the three presets cover it. Picking a preset builds the Action from name, `appId` and command, all editable afterwards. `ActionIcon` draws an Action: the detected app's icon through `EditorIcon` when it has an `appId`, the terminal glyph for a script, the generic document glyph for a custom app.

**Mutations.** `useWorkspaces` exposes `addWorkspaceAction`, `updateWorkspaceAction`, `removeWorkspaceAction`, `reorderWorkspaceActions`, `setActiveWorkspaceAction` and `promoteWorkspaceAction`, thin wrappers over the pure `applyWorkspaceActions`, `applySetActiveAction` and `takeWorkspaceAction`. Removing the active Action clears `activeAction`, and `setActiveWorkspaceAction` ignores an id that is not in the list. Promoting is two steps so an Action added in the same tick can still be promoted: the state updater only takes it out of the workspace and queues it (keyed by workspace and Action, so a repeated updater run is harmless), and an effect hands the queue to `globalActions.add`. If that write fails, the Action is put back at the end of its workspace list and a toast says so (if the workspace was closed in the meantime there is nothing to put it back into and the Action is lost).

**Running and stopping** (`actions/lib/actionRun.ts`, pure, plus the thin `useActionRunner` hook). `planActionRun(action, ctx)` decides what a run does and returns a plan: `blocked` (with a message the shell shows as a toast, or `silent` while the workspace sleeps), `spawn-app`, `already-running`, `reuse-tab` or `new-tab`. A script is typed into a terminal; an app is expanded with `expandCommandArgv` and launched with `native.actionSpawn(argv, cwd)`, with no terminal and no stop control. Before anything runs the plan checks `missingVariables` (a `{filepath}` with no file open blocks, naming the variable) and, for a script, `commandProblem` with the current values (`unsafeVariables`, quotes around a variable). The values come from `tabRawValues` of the focused tab (raw, home never turned into `~`, the workspace root and cwd as fallbacks) plus `branch` and `repo` from the cached git info. The script folder keeps the three modes of `resolveScriptCwd` (`workspace` by default, `context` for the last folder of the focused tab or agent worktree, `fixed`), validated with `scriptCwdProblem`, and the line typed is `buildScriptInput(expandCommandShell(...))`, with the shell chosen by `scriptShellFor`.

No Action is bound to a tab in the data. Which tab a script last ran in is a runtime link (`actionStateStore.ts`: `linkActionTab`, `unlinkTab`, in memory, never saved), and `App.tsx` drops it when the tab is disposed. A script reuses its linked tab only while that tab still exists, is a terminal and has no command of the user's own running in it; otherwise it opens a new terminal tab, so a busy, closed or non-terminal tab never keeps it from running. The new tab goes to the workspace scripts pane (`Workspace.scriptPaneId`), or splits one below the active pane the first time, or lands in the active pane when `workspacePaneLimit` is reached. A run that finds its script still running reveals and flashes the tab instead of starting a second run. Stop (`planActionStop`) sends Ctrl+C to the linked tab and sets the mark to `waiting` when the shell has reported the command (so the end-of-command event clears it) or clears it at once otherwise, like the old Stop. Stop only acts while the Action's tab still carries its running mark: once the script ended the mark is gone, and whatever the user started in that tab since (vim, another dev server) is never interrupted. The link and the mark of an Action are dropped by `removeWorkspaceAction` and by `updateWorkspaceAction` when it turns a script into an app (`unlinkRemovedActions`, outside the state updater), so a deleted running Action leaves no mark that nothing can stop; promoting does not drop them, as the Action goes on running as a global one. `focusActionTab` brings the tab into view with `planTabReveal` (another workspace is switched to; in the user's own pane the tab is activated since a pane shows one tab; any other pane is revealed without taking focus).

**Context menus** (`actions/RowActionsMenu.tsx`, entries in `actions/lib/contextActionEntries.ts`). The context menu of an explorer row (folder or file, including the explorer root row), a source-control row (staged folder or changed file), a path-bar segment (directory segments of terminal and editor breadcrumbs, the file leaf of the editor one) and a tab of the tab strip or sidebar rows (terminal tabs folder actions; editor, markdown, git-diff and git-commit-file file actions, with the tab path resolved absolute through `tabFilePath`) carries an "Actions" submenu (`RowActionsMenu`), always the first entry of the menu. The provider `ActionMenuProvider` wraps the app shell in `App.tsx` with the runner's `run` (extended with a `RunOverlay`: values, folder and spawn cwd for that place) and the active workspace. `useContextActions` sees the row as the tab an Action would run from: a folder row is a terminal in that folder, a file row an editor on that file, so `buildCommandVars` is evaluated exactly once, with branch and repo from the cached git info of `dirGitStore` (a folder outside a repo mutes the branch Actions instead of hiding them; the folder is demanded under a `ctx-` owner, so a command run from Kex refreshes it while the menu is open). `contextActionEntries` filters by target, read from the variables the command uses (`actionTarget`: `{filepath}`/`{filename}` make a file Action, `{cwd}`/`{dir}`/`{branch}`/`{repo}` a folder one, and `{workspace}`/`{host}` or no variables a workspace one): a folder row offers only the folder Actions, a file row only the file Actions, and workspace Actions never appear here (they are Header-only), so an Action whose remaining variables cannot be filled where it is open is shown muted with its availability reason (never runnable). Each row's second line carries the value the row gives the name's variable (`barSubtitle`), not the raw template; for `{workspace}` without a configured root it reads "Workspace Root not configured" instead. With no usable Actions for that row the submenu is not rendered. When the focused tab matches no Action's target at all (a workspace whose Actions are all file Actions with a terminal focused, say) the bar renders nothing but the hover-revealed "+ Action" trigger.

Running state is per Action: `useActionStates()` (`useActionStates.ts`, `useSyncExternalStore` over the links and the per-tab script marks of `terminalEphemeralStore`) returns `running` or `waiting` per Action id, with an idle Action absent and the same map reference while nothing visible changed. `workspace.run` (F12) calls `toggleActiveAction`: it picks the active Action (`pickRunnableAction` skips Actions with an empty command and falls back to the first one with a command) and runs it, or stops it when it is already running; a workspace with no Actions still falls back to the old Scripts until they are removed.

**Editing Actions** (`actions/ActionsEditor.tsx`, `ActionRow.tsx`, `AddApplicationMenu.tsx`; pure rules in `actions/lib/actionForm.ts`). One editor serves both scopes: the Actions tab of the workspace dialog (`WorkspaceSettingsDialog`, opened by the `workspace.runScripts` palette entry, now titled "Configure workspace actions") and Settings > Actions (`settings/sections/ActionsSection.tsx`, section id `actions`). Rows hold nothing that chooses a kind: the kind is picked on creation from the two add buttons and cannot change afterwards, deleting and recreating is the way to switch. "+ Add Command" starts an empty script draft; "+ Add Application" opens `AddApplicationMenu`, a searchable command combo over `suggestionsFromDetected` with the app icon on every entry, where a preset is handed to the store immediately and the custom app starts an empty app draft. Each row has a name, the command with a collapsible list of its variables (`commandVariableDocs`: cwd, dir, branch, repo, workspace, file, path, host) that inserts at the caret and shows the live value of the focused tab, for scripts the folder choice with its `scriptCwdProblem` error, and the "Own button in the header" checkbox; the row icon tells script from app. `actionProblems` separates problems that block (an unsplittable command, a bad fixed folder) from notes about the current context (`missingVariables`, `unsafeVariables`), which never stop saving. A new command row is a draft held in the editor and reaches the store only once it has a command, because `addAction` refuses an empty one; closing the editor forgets the drafts. Workspace rows have a Make Global button whose popover explains that a global Action moves to Settings and is available in every workspace, and confirms from its own button (`promoteWorkspaceAction`). The name box always shows the saved name and never saves an empty one; an Action never takes its internal id as a name, and an unnamed one is labelled by its command. The command box keeps what is typed apart from what is saved (`commandDraft`, `commitCommand`): an empty draft is flagged "Command is required" and never saved, so the stored Action keeps its last valid command, and once the box loses focus it shows the stored command again; the draft is saved on blur, when a variable is inserted and when the row unmounts, so closing the dialog or Settings does not lose it. A command example line sits under the list, where the input placeholders used to carry it. A new row keeps its place, and its focus, under the same key until the store shows an Action with its id; if the write fails the row stays and can be saved again. Settings edits go through `globalActions.change(fn)`, which runs the pure edit on the latest list inside the same write queue as `add`, normalizes the result, skips the write when nothing changed, and on a failed write restores the list unless a later edit already built on it. Removing or retyping a global Action calls `unlinkRemovedActions` with the before and after lists it returns. `change` can report a failure for an edit whose own write succeeded, when an earlier write it was queued behind failed: the list shown goes back and the user sees one extra error. That is accepted as rare. Closing a workspace counts its Actions with a command in `actionsToDelete`, so the close dialog warns about them and `isBlankWorkspace` keeps a workspace that holds any.

**The Header bar** (`actions/ActionsBar.tsx`, model in `actions/lib/actionsBar.ts`, data hook `lib/useActionsBar.ts`). The Header shows the workspace Actions first and then the global ones, each in the user's order. The pure `buildActionsBarModel` splits them into own buttons (`ownButton`, scripts and apps mixed, in order), a Scripts menu and an Apps menu, and marks each item with its run state (`running`, `waiting` or idle), whether it is the active one (`activeAction`, the one F12 runs) and a `disabledReason`. `actionAvailability` computes that reason with the same checks the runner uses (`commandProblem`, `missingVariables`, and for scripts `unsafeVariables`) and words it as what is missing: "needs an open file", "needs a workspace root", "needs a git branch". What shows depends on the focused tab through `actionShownAt`: a file Action appears only when the focused tab has a file (editor, markdown, git-diff, git-commit-file), a folder Action only when a terminal is focused, and a workspace Action always; a script that is running or waiting stays visible whatever the focused tab is, so it can always be stopped. The second line of every rendered name is the value the current place gives the name's variable (`barSubtitle`): the folder, the open file or the workspace root; when the workspace root is missing the line reads "Workspace Root not configured" and the right-hand reason is skipped for exactly that case (the subtitle already tells it, and only then: a name without the `{workspace}` suffix keeps its reason). The grouped menus size to their rows (`w-auto min-w-64`, capped at `max-w-96`) instead of inheriting the trigger width, which used to cut the rows. Below `COMPACT_WIDTH` (720 px, `isCompactBar`) the own buttons fold into the two menus so the bar never pushes the search box and the window controls out. With no Actions at all the bar is a single "Actions" button that opens the Actions tab of the workspace dialog. The dashed "+ Action" trigger sits at the left end of the bar; with Actions it hides and comes back on bar hover (staying visible while its menu is open, because the positioned menu content is anchored to it), and its menu picks the scope first: "Add global action" opens Settings > Actions with an empty focused script draft, "This workspace only" the same draft in the workspace dialog.

A script has two hit areas with their own hover: the name and the play or stop zone (`ScriptControl`, green for run, red for stop, a spinner while stopping). Clicking the name brings the script's tab into view when it has one (`focusActionTab`) and runs the script otherwise; the play or stop zone always starts or stops. The same two zones repeat in every row of the Scripts menu. An app is a single button (or row) with its icon that launches it; apps have no stop. The context (`useActionContext`) is memoized by content, so the bar re-renders only when a value an Action can read changes.

Closing or hibernating a workspace asks about the scripts that are running by looking up the Action each terminal belongs to (`liveScripts` and `scriptActionOf`, over the workspace's Actions and the global ones), since the link from a script to its tab lives in memory and not in the workspace.

## 4. Technical decisions with user-visible effects

### 4.1 Tabs are never unmounted

When you switch tabs or panes, the outgoing tab is hidden with CSS classes. It is never unmounted from the React tree. This means:

- PTY sessions keep streaming in the background. A running `npm run dev` in one panel continues while you work in another.
- Tab state (scroll position, xterm buffer, editor content, unsaved changes) is preserved exactly as you left it.
- Memory usage is proportional to the total number of open tabs across all workspaces and panes. Each terminal tab holds a live xterm instance; each editor tab holds CodeMirror state. There is no sleep mechanism for idle tabs.

### 4.2 Tab close confirmation

Every close path (tab close button, the close shortcut, and Close All / Close Other Tabs) runs through one sequential queue, `closeTabs(tabIds)` in `useTabCloseGuards`. The pure core (`hooks/closeQueue.ts`) closes tabs one at a time: a terminal with a live foreground process or a dirty editor pauses the queue on a confirmation dialog, and a cancel stops the whole run before closing the current tab. Terminals only prompt when the `warnOnCloseTabWithRunningProcess` preference is on (default on); the terminal dialog's "Don't ask me again" checkbox flips that preference off. The editor dialog offers Save / Don't save / Cancel; Save writes through the editor handle before closing, and a failed write stops the queue without losing the buffer. After any run, focus returns to the active tab's terminal or editor.

### 4.3 Workspace authorization

Before any git or shell command can run against a directory, that directory must be in the `WorkspaceRegistry`. The registry is populated automatically when you open Kex in a directory (via CLI argument or the OS file manager context menu), and when you explicitly navigate to one via the terminal (`cd` triggers an OSC 7 event that registers the new cwd). `workspace_authorize` is the IPC command for explicit authorization.

The registry lives in memory only - it does not persist across restarts. Each session builds it up as the user navigates.

The practical effect: if you try a git operation in a directory you haven't navigated to in the terminal yet, the git-related features (diff decorations, source control panel) will fail with "path is outside the authorized workspace" until you `cd` there in a terminal first.

**Subdirectory cwd and git repo root.** When the terminal cwd is a subdirectory of a git repo (e.g., cwd is `/proj/src`, git root is `/proj`), `resolve_repo_in_authorized` and `panel_snapshot` deliberately do NOT add the repo root to the registry -- doing so would silently escalate the authorization scope to the parent and grant access to sibling directories the user never navigated to. Instead, git commands use `has_child_authorized`: a repo root is considered authorized for git operations if any currently-authorized path is strictly under it. This keeps the registry tight while allowing the SCM panel and all git commands to work correctly from a subdirectory.

**`fs_*` commands are not workspace-gated.** File read/write commands (`fs_read_file`, `fs_write_file`, `fs_stat`, `fs_create_*`, `fs_rename`, `fs_delete`, `fs_read_dir`, `fs_search`, `fs_grep`, etc.) accept any path the OS allows. This is a deliberate decision: the explorer only surfaces paths the user has explicitly navigated to, so there is no app-level vector for a user to accidentally open a path outside their workspace. Terminal commands can access arbitrary paths regardless of any app-level guard, so a gate here would only stop the app's own UI - not a shell running inside a pane. A deny-list for secret paths (`.ssh`, `.env`, `*.pem`, etc.) would be worthwhile if Kex ever runs autonomous agents that make IPC calls directly; the right insertion point is `guard_read`/`guard_write` helpers at the top of `fs/file.rs`, applied before `resolve_path`. Until then, `capabilities/default.json` is the real boundary: only code in the webview bundle can call these commands.

### 4.3 Windows: ConPTY spawn serialization

On Windows, creating and closing a ConPTY session serializes through a `CONPTY_LIFECYCLE_LOCK` mutex (`pty/session.rs`). Overlapping pseudoconsole lifecycle calls corrupt the new console so its shell never pumps output. This means: if you open several tabs very quickly on Windows, the tabs open in sequence rather than in parallel. The delay is typically under 200ms per tab and is only perceptible during rapid tab creation.

### 4.4 Windows: Job Objects for process cleanup

Every ConPTY child process on Windows is assigned to a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. When the Job handle is released (Kex closes, crashes, or is killed), the OS terminates the entire process subtree of that shell session. Without this, `npm run dev` started inside a PowerShell terminal would continue running after Kex exits, as `TerminateProcess` only kills the immediate child.

Closing a tab from the UI (the explicit close button) also kills the immediate child. The Job Object handles the "Kex process died unexpectedly" case.

### 4.5 OSC trust model

Kex's shell integration emits and parses OSC 7 (cwd), OSC 133 (prompt/command boundaries), and OSC 0/2 (window/icon title). The cwd from OSC 7 updates the explorer root. OSC 0/2 title is written to `oscTitleStore` (in-memory, not persisted) and shown in the pane tab. This means a malicious command outputting a crafted OSC sequence could theoretically spoof the displayed cwd or tab title. The shell integration scripts are trusted; arbitrary terminal output from untrusted remote connections (SSH to untrusted hosts) is a trust boundary to be aware of.

**Tab titles** (`tabTitle()` in `src/modules/workspaces/lib/tabTitle.tsx`). The title is, in order: the tab's own `title` (explicit user rename, a template; see Title templates), else the **default template of its kind**, else a fixed name when that template expands to nothing (`shell`, `Browser`, `Git History`, or the file name for file tabs). The default templates are configurable in Settings > Appearance > Tab and workspace titles (`TitleTemplatesBlock`: one `Label: [input]` row per kind, whose field always holds the template in force so the default itself can be edited in place; what is typed is saved after 250 ms of quiet (and on blur or when the section closes) because each save writes the file and notifies every window; the row remembers what it last sent and ignores the echoes of older writes while one is still on its way back, a value equal to the default or an empty one saves nothing so the default keeps following Kex, and a field being typed in is never overwritten by a change that arrives from the store; and a single table below the rows with every variable, an example value for each and the `{a|b}` / `{var? text}` syntax, grouped so the ones valid everywhere come first (`TITLE_VARIABLE_DOCS` carries the group and the example); prefs `titleTemplateTerminal`, `...Agent`, `...Editor` (editors and markdown), `...Diff` (git diffs and commit files), `...Browser`, `...GitHistory`, `...Workspace`; an empty pref means the factory default). `defaultTitles.ts` holds the factory ones, which reproduce what Kex showed before they were configurable except the git history, which now names its repository:

| Kind | Factory default | Meaning |
|---|---|---|
| terminal | `{cmd\|osc?{cmd\|osc} · {dir}{:}{dir}{branch? · {branch}}}` | what is running (foreground command from OSC 133 C, else the title the program set with OSC 0/2) followed by the folder only: `npm run dev · kex`; an idle shell shows where it is, the folder plus the branch inside a repository: `kex · main`, or just `kex` outside a repo |
| terminal with an agent | `{osc\|session\|{agent}}{branch? · {branch}}` | OSC title, else the agent session title, else the agent name, followed by the branch inside a repository: `✳ Fix login · main`, `claude` |
| editor, markdown | `{file}` | file name |
| git diff, commit file | `{file}` | file name |
| browser | `{url}` | address |
| git history | `Git History{dir? · {dir}}` | `Git History · kex`; the folder is the repository root |
| workspace | `{dir}` | name of the focused tab's directory |

A terminal tab knows its folder from the moment it is created, not from the first OSC 7: every place that opens one passes `cwd`, and `resolveNewTerminalCwd` ends its fallback chain at the launch folder and then home, which is what the shell picks on its own; OSC 7 only follows later `cd`s. `pty_open` answers `{ id, cwd }`, the folder Rust resolved for the spawn (the given cwd when usable, else the launch folder, else home, in the same chain `apply_common` follows), and `applySpawnCwdReport` seeds `lastCwd` from it the moment the PTY opens, so a tab saved with a stale or deleted folder shows the folder the shell really opened in instead of waiting for the first OSC 7. That is why the defaults above can assume "where" exists and carry no guard for an empty folder. A terminal is an agent tab when `TitleSources.agent` is set (an agent session exists for it). The foreground command is deliberately not in the agent default: the shell reports it as literally `claude ...`, which would mask the live OSC title. Claude Code uses OSC 0/2 to propagate its AI-generated conversation title (`ai-title` field in the session JSONL); it emits `✳ Claude Code` on startup and `✳ <ai-title>` once generated, and spinner frames (`⠂ Claude Code`) are transient. `agentSession.meta.sessionTitle` is set once by the `SessionStart` hook payload, often empty and never updated, so it only fills the gap before the first OSC title.

Both the tab bar (`PaneTabBar`) and the header (`WorkspaceTitle`) render this same value through the shared hook `useAgentTabTitle()` (`src/modules/workspaces/lib/useAgentTabTitle.ts`), so they cannot diverge. See `docs/WORKSPACES_GOTCHAS.md` Bug 9 for the investigation that led here (the header used to show only the agent name because it called the non-agent `tabTitle()` directly).

**Title templates.** The name a user gives a tab (`Tab.title`) or a workspace (`Workspace.title`) may contain variables, which are expanded every time the title is rendered; the stored value is the raw template, and the rename fields show it raw (next to every rename field, a "Show templates" toggle (`RenameTemplates.tsx`, expanded also by the rename shortcut itself, which while renaming toggles the list instead of saving via `resolveRenameShortcut` -> `"toggle"`, one `templatesOpen` boolean per rename store) opens the variables the subject can have (`titleVariablesFor.ts`, pure: `titleVariablesFor(subject)` filters `TITLE_VARIABLE_DOCS` by group, so a browser tab offers `{url}` and `{host}` but neither `{cmd}` nor the folder ones (`{cwd}`, `{dir}`, `{branch}`, `{repo}`, group `place`, which a browser has no value for), file kinds drive the list through `titleSubjectForTab`), one per row in the look of the variables table in Settings, each with the value it holds for the renamed tab right now, computed live (agent session, running command, OSC title, git in the tab's folder, host; for a workspace the values of its focused tab, falling back to its folders), and each row clickable to insert it into the input where the caret is (`insertTitleVariable` / pure `insertToken`; a `preventDefault` on mousedown keeps the focus and the caret in the input, and `onInserted` lets the field sync its live title draft); under the list a "Defaults" row opens Settings (title templates section), and the WorkspaceBar rename field and the workspace Properties dialog show the same component as a local list without the shortcut. A title without braces is shown as typed, so nothing needed migrating. The pure expander is `expandTitle` in `workspaces/lib/titleTemplate.ts`: `{{` and `}}` give literal braces at the top level (inside a group every brace opens or closes), a variable that is not defined in that scope stays literal (so a typo is visible, and `{tab}` in a tab title is not a variable), and a result that is empty after trimming falls back to the default title. Two forms go beyond plain variables. `{a|b|c}` is a fallback: the first alternative whose value is not empty; an alternative with anything besides letters is itself a template (`{osc|{agent} · {dir}}`). `{a|b?then}` is the conditional, a ternary: `then` (which may hold variables and further groups, and is taken literally, spaces included) is rendered only when `a` or `b` is not empty, so `{dir}{branch? · {branch}}` shows no dangling separator outside a repo; a `{:}` inside it starts the else, rendered when none has a value (`{branch? on {branch}{:} in {dir}}`), and a `{:}` nested in an inner conditional belongs to that one. A `{:}` outside any conditional is plain text. A group whose head is only variable names followed by `?` is always a conditional, so a fallback alternative of plain text cannot end in `?` right after a name (`{osc|why?}`). Blank values count as empty and an unknown name leaves the whole group literal. The parser builds a small node tree once (`parse`), shared by `expandTitle` and `titleVariablesUsed`. Variables: `{cwd}` (home shown as `~`), `{dir}`, `{branch}` (empty on a detached HEAD or outside a repo), `{repo}` (name of the repo root), `{workspace}` (full path of the root of the workspace the tab belongs to, home shown as `~`, empty without a root; every tab reads it from `tabWorkspaceRootStore`, which `useWorkspaces` refills on each change of the workspaces state), `{cmd}` (running command, terminals only), `{file}` (name of the file), `{path}` (full path of the file, home shown as `~`, file tabs only; `tabRawValues` in `titleVars.ts` gives the location values untouched, without `~`, for building commands), `{agent}`, `{model}` (model of the agent's last answer, kept live, see IPC.md), `{host}`, `{osc}` (title set by the running program), `{session}` (the agent's session title), `{url}` (browser tabs), and for workspaces only `{tab}`.

**Command templates** (`src/modules/actions/lib/commandTemplate.ts`, pure). An Action's command ("pycharm {cwd}") is written in the same grammar and with the same variables as a title, through the same parser (`renderTemplate` and `missingTemplateVariables` in `titleTemplate.ts`), but it is run, not shown, so the rules differ: whitespace and line breaks are kept, an empty result stays empty, the values are raw (home is never turned into `~`, the caller passes a plain name-to-value map) and each value is quoted for how the command runs. An app is launched without a shell: `expandCommandArgv` splits the command first (`splitArgv`: single and double quotes like a POSIX shell, none of its expansions; a backslash is always literal, so `C:\tools\x.exe`, `\\server\share` and `"C:\dir\"` survive, which means a quote cannot be escaped (wrap it in the other kind) and a space in a path needs quotes, never a backslash) and substitutes the variables inside each argument afterwards, so a value with spaces or quotes can neither split nor add an argument; a group with spaces in it needs quotes around it. A script is typed into a terminal: `expandCommandShell` quotes every value for the shell (`posix` with `quoteShellArg`, `powershell` by doubling single quotes, curly ones included), so the user writes `{cwd}` bare. A known variable placed inside quotes the user wrote, in a heredoc body or right after an escape character is refused (`quotedVariables` in `quotedVariables.ts`; `expandCommandShell` throws and `commandProblem(command, shell)` reports it): it would be quoted twice and, inside double quotes, a `$(...)` in a value would run. The scan tracks single, double and `$'...'` quotes, `$(...)` nesting (a quote inside it is its own context), comments, heredoc bodies and, for PowerShell, the typographic quotes, the backtick and `<# #>`; braces that are not known variables (`awk '{print}'`) are ignored. It is a scanner, not a parser, and quoting does not help in contexts that re-evaluate the expanded text (arithmetic `(( {cwd} ))`, subscripts `a[{cwd}]=1`, `${x:0:{cwd}}`, where a single-quoted `$(...)` still runs), so there is a second layer that does not depend on the command: any written value holding `$`, a backtick, a single or double quote or (posix only; PowerShell takes a backslash as an ordinary character) a backslash makes `expandCommandShell` throw `{name} cannot be used in a script right now`, whatever the command looks like (PowerShell is as strict about `$`, backtick and every quote, typographic ones included; it could not be tested). Such paths are rare and refusing them is safer than guessing which contexts a command has. `unsafeVariables(command, vars, shell)` returns the written variables with an unsafe value and `commandProblem(command, shell, vars)` reports them, so the UI can say that the value, not the command, is what stops the Action; only the values actually written count (a `{a|b}` fallback not taken is not). App commands (`expandCommandArgv`, no shell) are not affected. Control characters (C0, DEL, C1 and the Unicode line and paragraph separators, so also tab and newline) are stripped from every value before quoting, because the line is typed into a PTY where a newline ends the command and ESC acts on the terminal. A value that starts with a dash is still an option to the program, so a command that can receive one puts `--` before the variable (`git add -- {path}`). Shell mode must only run once `missingVariables` is empty: an empty value writes nothing and its argument would vanish silently. `missingVariables` lists what the command needs and has no value for (a plain variable or a `{a|b}` group with every alternative empty; `{a? text}` parts are optional) and is what disables an Action; `commandProblem` explains an empty command or an unterminated quote. Tests run the generated line through real bash and zsh with paths holding spaces, quotes, `$`, backticks, newlines and globs.

While a rename field is open, what is being typed shows live in every place that title appears: the field writes it to `titleDraftStore.ts` (per tab or workspace id), `useAgentTabTitle` and `useWorkspaceTitle` read it in place of the saved title, and closing the field, saving or cancelling, clears it, so cancel just reverts. An emptied draft previews the default title. A workspace is created with an empty `title`, which means "use the workspace default template"; renaming to an empty name returns to it, and existing workspaces keep the text they have. The default of each kind also counts for the git demand below: a mounted title asks for the branch when its effective template (own or default) uses `{branch}` or `{repo}`. `titleVars.ts` derives them from a tab plus `TitleSources` (running command, git info, agent, home, host); a workspace has no location of its own, so `workspaceTitleVars` takes everything from its focused tab (active pane's active tab, `focusedTab()` in `splitNode.ts`), falls back to `cwd` or `workspaceRoot` when that tab has none (a browser), and `{tab}` is that tab's resolved display title. Tabs resolve through `tabTitle()` and `useAgentTabTitle` (so the pane tab, the header and the WorkspaceBar rows agree); workspaces through `useWorkspaceTitle` (WorkspaceBar, header, hibernated overlay) or its one-shot twin `workspaceTitleNow` (drag overlay, move-to menu, notifications). The branch comes from `dirGitStore.ts`, a per-directory cache over `git_resolve_repo`: a directory is only queried while a mounted title that uses `{branch}`, `{repo}` or a templated `{tab}` has asked for it (`useDirGit`). The factory terminal and agent defaults use `{branch}`, so every mounted terminal asks by default: one `git_resolve_repo` per distinct directory when a folder is first shown, then one for the folder of the terminal whose command just ended, so the steady cost follows the commands you run and not the number of open terminals; the other defaults ask for nothing. On a local workspace the branch, upstream and worktree flag come from `git/direct.rs`, which reads `.git` itself (HEAD, commondir and the config) without spawning a single git process; WSL workspaces and anything the direct read cannot answer (a `GIT_*` override, an unparsable HEAD, an include section, extensions, a non-default fetch refspec, reftable ref storage) fall back inside `resolve_repo_in_authorized` to the git-process path, which answers as before, so the workspace authorization checks never change. Titles only read the cache; a query happens on first demand of a folder, 400 ms after a command ENDS in a tab that shows git (`subscribeToCommandFinished` reports the tab id, and only the folders that tab asked for are queried, since a checkout does not change the cwd), and when the window regains focus (every demanded folder, to catch changes made outside Kex). A branch found to have changed in one folder is copied to every cached folder of the same repository root without another query, so an editor tab follows a checkout made in a terminal. Listeners are notified only when a branch really changed, and they exist only while something is demanded. `{host}` and the home directory are read once by `systemInfoStore.ts`.

**Tab notes.** Any tab can carry a markdown note (`TabCommon.note`, persisted with the tab, no migration) that floats over its pane. The `tab.note` shortcut (Cmd+B by default) toggles it for the active tab: with no note it creates an empty one, open and focused (`tabNoteStore.focusTabId`, so switching to a tab that already has its note open never steals focus); with a hidden note it opens it; with an open note it hides it, and hiding a blank note drops `note`, `noteOpen` and `notePos` (pure `toggleTabNote` in `lib/tabNote.ts`). `noteOpen` is persisted too. The note is drawn by `FloatingTabNote` as an overlay rendered from `PaneView` inside the pane root (not in the tab bar, which scrolls horizontally), only for the pane's active tab, and it is edited in place with `CodeMirrorEditor` in Rich mode (Live Preview, `maxHeight` so it sizes to its content), lazy-loaded; typing stays in the editor and is written to the tab with `setTabNoteText` on a 300 ms debounce, because a workspaces state update per key re-renders the whole app; the editor is seeded once with the note text, and `flushTabNote(tabId)` (`tabNoteStore.ts`) forces the write before anything reads `tab.note` (the `tab.note` shortcut, blur, the close button, unmount). Its position is relative to the pane and always clamped (`lib/notePlacement.ts`): with no `notePos` it sits just under the tab bar aligned with its tab, so it follows tab-strip scroll and reorder; once dragged by its header strip (pointer capture, local state while dragging, a single `moveTabNote` commit on pointerup, none for a click without movement) it keeps a fixed `notePos`. Its size is also user-set: a grip in the bottom-right corner (same pointer-capture pattern, local state while resizing, a single `resizeTabNote` commit on pointerup that also makes the note sticky) stores `TabCommon.noteSize`, clamped by `clampNoteSize` to a minimum and to the pane's right and bottom edges from the note's top-left; with no `noteSize` the note keeps the default width and content-sized height, and a docked note (an inactive tab's, or one previewed from a WorkspaceBar row) ignores `notePos` but does use `noteSize`, capped to the pane. The note icon keeps its on/off colour while hovered (bright when the note is open, dim when not), so the hover never hides the toggle state. Measurements are refreshed from `ResizeObserver` (pane and note), the tab strip's scroll event and the tab id list, never per frame. The overlay root is `pointer-events-none`; the note carries `data-tab-note`, which `PaneView`'s mousedown capture ignores so clicking in the note does not refocus the terminal. The rename popover (`tab.rename`) edits only the title; Enter, Escape and blur (however it is lost, including the app regaining OS focus, which no longer steals the field's focus: `domFocusHoldsOsRefocus` guard in `osRefocus.ts`) save and close it, a second press of the shortcut toggles the templates table (`resolveRenameShortcut`). Notes have two modes. A sticky note is the persisted `noteOpen` one of the active tab: it has a close button (`hideTabNote`: hides it, or drops it when blank) and stays until closed or toggled with the shortcut. Hovering the tab icon shows a transient hover note (`useNotePreview` in `lib/useNotePreview.ts`, owned by `PaneView`) even when the note is closed or its tab inactive; it has no close button and goes away by itself: when the pointer leaves the icon and the note (delayed so the pointer can reach it, and held while the editor has focus) or as soon as the editor loses focus, whatever was typed being kept. On the active tab it appears at its usual place and can be dragged, which makes it sticky (`moveTabNote` sets `noteOpen`); on another tab it is docked under that tab, ignoring `notePos`, and cannot be dragged. A blank note that loses focus is dropped (`dropBlankTabNote`). A tab with a note shows a `StickyNote03Icon` button after its title that toggles the note; the tab context menu has Add/Show/Hide Note and Remove Note. The WorkspaceBar rows (`WorkspaceDetailList`) show the same icon for a tab with a note, just before the close/status mark, and hovering it previews the note the same way for every tab: a `FloatingTabNote` with `dockTo="side-row"`, portaled to `document.body` and docked to the right of its row (`sideRowNotePos`), not draggable and not resizable. When that tab is the active one of a pane of the active workspace (`WorkspaceItem.visibleTabIds`), the pane hides its own copy of the note for as long as the preview is up (`tabNoteStore.sidebarHoverTabId`, set by `WorkspaceDetailList` and read by `PaneView`), so the note never shows twice. Clicking the icon of a docked tab toggles `noteOpen`: turning it on keeps the preview under the pointer, now with a close button (`closable`) that hides the note; turning it off also drops the preview. The body of that menu lives in `TabContextMenuItems.tsx` and the rename field in `TabRenamePopover.tsx`, both shared by the pane tab and the WorkspaceBar rows; the store records where a rename was started (`RenameOrigin`: `pane` or `sidebar`) and only the matching surface opens its field. The tab menu has no New entries: they live in the menu of the `+` button at the end of each pane tab strip (`NewTabMenuButton.tsx`): a click still opens a terminal tab, resting the pointer on it for `HOVER_SWITCH_DELAY_MS` (600 ms, the pure timer `createHoverSwitch` that also drives hovering a workspace while dragging a tab) or right-clicking opens a menu with New Terminal / Browser Tab, Split Right and Split Down. The menu is a controlled `DropdownMenu` whose trigger is an inert anchor, so Radix never toggles it from the button's own events; a click, leaving the button or a drag starting (`useWorkspaceDnd().draggingItem`) cancels the pending timer, and the hover is not armed while something is being dragged. The delay is not a setting.

**Icon and color pickers.** The workspace and tab menus (and the workspace properties dialog) share `IconPaletteGrid` and `ColorPaletteGrid`. The icon picker shows the curated `WORKSPACE_ICON_PALETTE` and has a search box that finds any Hugeicons icon: the full set (about 5,500 icons, a 5.5 MB / 1.25 MB gzip chunk) is loaded lazily by `iconCatalog.ts` the first time someone searches or a saved icon is not in the palette, and `useIconCatalogVersion` re-renders the components that paint an icon (`tabIcon`, `WorkspaceMark`, the WorkspaceBar rows) when it arrives. Icons are stored by name (`Tab.icon`, `Workspace.icon`). The color picker is "No color", three rows of seven swatches (`COLOR_SWATCHES`, apart from `WORKSPACE_COLOR_PALETTE`, which seeds the automatic workspace colors) and a free editor (hex field and native picker). A tab can have its own `color` (`TabCommon.color`): it tints the icon and draws a short stripe on the left in the pane tab strip; in the WorkspaceBar rows it does the same while the row is not focused, and when the row is focused the workspace color wins and the tab color only fills the focus chip if the workspace has none (`sidebarChipColor`). The line on top of the active tab of the focused pane is the tab color, else the workspace color (`useWorkspaceColor`, provided per workspace by `WorkspaceView`), else the theme indicator (`tabTopLineColor`).

`oscTitleStore` (`src/modules/terminal/lib/oscTitleStore.ts`) is a module-level singleton with `useSyncExternalStore`-compatible API. It is keyed by `tabId`, is never persisted, and is cleared on session dispose and respawn. OSC 0 and OSC 2 are both handled (both set the window title per the terminal spec); the handler is registered via `registerTitleHandler` in `osc-handlers.ts` and wired in `useTerminalSession.ts` alongside the existing OSC 7 and OSC 133 handlers.

### 4.6 Forward-slash canonical paths

The frontend stores all paths in forward-slash form. OSC 7 on Windows emits `/C:/Users/foo`; Kex normalizes it to `C:/Users/foo` at parse time. `homeDir()` on Windows returns backslashes; `App.tsx` converts at the boundary. Any code consuming a path that might originate from the OS must normalize separators with `.split(/[\\/]/)`. This is documented in `CLAUDE.md` and enforced in code review.

The reason: consistent string equality for path comparison (e.g., preventing the file explorer from flashing when `tab.cwd` arrives). Using two representations and forgetting to normalize in one place causes subtle bugs.

### 4.7 React 19 Strict Mode double-mount

In development (`pnpm tauri dev`), React 19's Strict Mode double-invokes `useEffect`. This means a PTY is opened and immediately closed before the real one opens. You will see `pty opened id=1` then `pty closed id=1` followed by `pty opened id=2` in dev logs. This is expected and does not happen in production builds.

### 4.8 Terminal font resolution (VS Code model)

There is no runtime font detection. `src/lib/fonts.ts` resolves the terminal font the way VS Code does: a per-platform default stack (Menlo then the bundled JetBrains Mono and Monaco on macOS, JetBrains Mono then Consolas on Windows, JetBrains Mono then Droid Sans Mono/DejaVu Sans Mono on Linux, then the bundled Symbols Nerd Font Mono, ending in `monospace`), and a free-text "Font family" setting that accepts a comma-separated list. A non-empty preference is normalized (names with spaces are quoted, required by the canvas font shorthand the WebGL atlas uses) and always prepended to the default stack, so a typo or uninstalled font can never break rendering. The browser falls back per glyph through the list, which is also how Nerd Font icons resolve when the primary font lacks them. xterm runs with `customGlyphs` (pixel-perfect box-drawing/powerline glyphs drawn by the renderer, not the font) and `rescaleOverlappingGlyphs` (VS Code defaults; Nerd Font, powerline and emoji ranges are excluded from rescaling by xterm itself). Icon coverage does not depend on installed fonts: `src/assets/fonts/SymbolsNerdFontMono-Regular.woff2` (icon-only PUA glyphs vendored from nerd-fonts v3.4.0, ~1.1 MB, MIT) is declared in `src/styles/fonts.css`, preloaded by `ensureMonoFontsLoaded()`, and sits last in every stack, so prompt icons (powerline, devicons, octicons) render out of the box and user-set fonts inherit them through the appended default stack.

Earlier approaches that were removed: auto-detecting installed Nerd Fonts via `document.fonts.check()` (false positives in WKWebView, it reports fallback-renderable rather than installed) and via `document.fonts.load()` (worked, but a curated candidate list plus a dropdown is strictly worse than VS Code's free-text stack with per-glyph fallback).

The terminal and the code editor (CodeMirror) each expose independent "Font family", "Font size", "Letter spacing" and "Line height" controls under Appearance. The editor settings are resolved through the same `resolveMonoFontFamily()` model and applied as the `--editor-font-family`, `--editor-font-size`, `--editor-letter-spacing` and `--editor-line-height` CSS variables (`useEditorFont` writes them on the document root) which the editor theme in `editor/lib/extensions.ts` reads, so a change re-renders every mounted editor without rebuilding its state. The terminal settings are pushed onto every live xterm slot from `useTerminalSession` (`applyFontSize`/`applyLetterSpacing`/`applyLineHeight` in `rendererPool.ts`). Both "Font family" fields show the platform default verbatim when unset and store an empty string for it (so the default still adapts per OS), with a reset button that clears back to it. Font size sliders are bounded to 8-18 px in 0.5 px steps (terminal sizes snap to half-pixels after the zoom multiply, see `renderFontSize`), letter spacing to -4..4 px in 0.5 px steps, and line height to 0.8..1.8 in 0.1 steps. Editor font size, like the terminal, is multiplied by the UI zoom.

### 4.9 Markdown tabs are editable by default

Opening a `.md` file mounts Live Preview, a CodeMirror 6 editor that decorates the raw markdown text in place (`modules/markdown/codemirror/`). It is the only markdown engine: the TipTap and Milkdown WYSIWYG editors, the Streamdown-only "legacy" engine and the per-tab `markdownEngine` field were removed, so there is no engine setting and no engine sealed onto a tab. A tab persisted by an older version simply ignores the unknown field. Earlier Kex versions had preview-only `markdown` tabs where editing required a `Rendered | Edit` toggle; that toggle no longer exists, its keyboard gesture is now `editor.cycleView`, which rotates the modes of the tab (see 7. Frontend module map, "Tab kinds"). `[[Note]]` wiki links are planned in `livePreview.ts` (`planWikiLink`) and resolved at draw time through the `wikiLinkHost` facet (`livePreviewPlugin.ts`), which `useWikiLinkHost` fills from an `fs_glob` of the workspace's `.md` files and the `onOpenFile` tab callback; a view without that facet (the editor-tab overlay preview) shows the label as plain text. Source and Rich share one CodeMirror view, so they keep cursor and scroll for free; Preview is a second view, so `MarkdownTab` carries the reader's place across it by hand (`lib/viewPosition.ts`, in source lines): it saves cursor and top line on the way in, shows Preview at that line, and on the way out restores them exactly if Preview was not scrolled, or puts the cursor at the top of what was read if it was.

The tab has three modes, chosen in the path bar and rotated by `editor.cycleView` (`lib/viewCycle.ts`): Source (raw text), Rich (the Live Preview decorations) and Preview (read-only `MarkdownPreviewPane`: the Live Preview extensions with no line ever active, frontmatter shown as the same monospace lines as in Rich (so both views have identical line heights), link definitions hidden and a plain click opening a link). A markdown tab registers a handle (`registerMarkdownHandle`: `save`, `cycleView`, `toggleOutline`) that the global `editor.cycleView`, `editor.save` and `markdown.toggleOutline` handlers call for the active tab, so they work whatever has focus (unlike a keydown on the tab, which is lost when Preview unmounts the editor). Source and Rich share one CodeMirror view and only toggle the decorations through a `Compartment`, so cursor, scroll and undo history survive the switch; Preview unmounts the view.

### 4.10 Buffer ownership: `useDocument`

The tab reads and writes its file through the same `useDocument` hook (`modules/editor/lib/useDocument.ts`) as a plain `editor` tab, so the CodeMirror document is the single source of truth for the text. `MarkdownTab` keeps only the text typed since the last load, tied to the `doc` it was typed against (a reload swaps `doc` and the stale edit is ignored), so Preview and Outline can read it and a remounted editor starts from it. The buffer a tab carries across an unmount (`unflushedBuffers` in `useDocument.ts`, for example when the tab is dragged to another pane) is keyed by tab id, not by path: the same file open in two tabs would otherwise let one tab's unmount overwrite or adopt the other's cache. `EditorPane` and `useDocument` therefore receive `tabId` as well as `path`. The conflict flag (`conflict` + `keepLocalChanges`) and the auto-save timer live in `useConflictFlag` / `useAutoSaveTimer` under `src/modules/editor/lib/`.

### 4.11 Save round-trip policy

Live Preview never converts the text: it hides and decorates syntax markers but the document is the file's bytes, so opening a note and saving it without editing writes the same bytes, and frontmatter (key order, quoting, comments) is never reformatted. `lib/frontmatter.ts` only tells the decorations where the frontmatter block ends. Autosave and the close-tab guard only write when the buffer differs from the last-saved snapshot.

## 5. Known limitations

### 5.1 No SSH support (yet)

SSH is on the roadmap but not yet implemented. Kex does not manage SSH connections, key agents, or remote filesystems. You can of course `ssh user@host` in a terminal tab - the PTY runs it fine - but the editor, file explorer, and git panel all operate on the local filesystem (or the WSL filesystem on Windows). See ROADMAP.md.

### 5.2 No persistent terminal layout restore

Terminal sessions are not persisted across restarts. When you close and reopen Kex, terminal tabs restart with a fresh PTY in their saved `cwd`. Shell history within the terminal is whatever your shell persists natively (`.zsh_history`, `.bash_history`, etc.).

**Exception: agent sessions.** If the per-agent integration is installed (`agent_enable_claude_hooks` for Claude Code, `agent_setup_opencode` for OpenCode, `agent_setup_omp` for OMP, `agent_setup_pi` for Pi), Kex records the active session id and cwd at agent exit and restores it automatically on next launch by running the provider's resume command (`claude --resume '<id>'`, `opencode --session '<id>'`, `omp --resume '<id>'`, ...) in the terminal. See section 3.7a and `docs/AGENT_SESSION_RESTORE.md`.

### 5.3 No LSP / language server

The editor does not support Language Server Protocol. There is no hover documentation, go-to-definition, inline diagnostics, or refactoring from language servers. CodeMirror's built-in syntax highlighting and autocomplete work, but IDE-level language intelligence does not. This is a deliberate scope decision (see ROADMAP.md > Out of scope).

### 5.4 File explorer watch lag

The file tree watches for filesystem changes via `notify`. On some Linux filesystems (including certain WSL mounts) the watcher latency can be higher than on macOS (kqueue/FSEvents) or Windows (ReadDirectoryChangesW). A file created in the terminal may take a second or two to appear in the explorer.

### 5.5 Apple Silicon / macOS code signing

Kex is not yet notarized by Apple. The first launch on macOS Gatekeeper requires right-click > Open (or `xattr -dr com.apple.quarantine Kex.app`). Auto-updates are signed with minisign but not Apple-notarized.

### 5.6 Windows: no code signing

On first launch Windows shows "Windows protected your PC" (SmartScreen). Click "More info" then "Run anyway". This is expected until the project acquires a code-signing certificate.

### 5.7 Web preview is not a full browser

The preview pane renders local dev servers in a native child webview. It does not have navigation history, bookmarks, devtools, or extension support. It is not a replacement for opening your dev server in Chrome or Firefox. External URLs work but the experience is intentionally minimal.

### 5.7a Hibernated workspaces

`Workspace.hibernated` marks a workspace whose tabs are not mounted: its terminals have no PTY and
its editors are unmounted. The tabs stay in the persisted `paneTree` on purpose, so waking the
workspace restores the same layout and tabs. Limitations: scripts launched from an Action are
not relaunched on wake, unsaved editor edits are discarded, and an agent that cannot be resumed
follows the existing restore error path. Rendering details are in `docs/WORKSPACES.md`.

Startup: there is no startup preference. `initWorkspaceState()` restores every saved workspace as it was:
the ones that were hibernated (manually or by auto-hibernate) stay hibernated, the rest mount normally. Their
`lastActiveAt` is seeded into `activityStamps`, so auto-hibernate keeps counting their inactivity from the
last real activity instead of restarting the clock. Memory is controlled by auto-hibernate alone.

Reopen Closed Tab or Workspace (`reopenClosed` in `useWorkspaces.ts`, pure logic in `closedStack.ts`) undoes the
last close, whatever it closed. The closed stack (in memory, capped at 10) holds two kinds of entry:

- A tab entry (`closeTab`) reopens only in the workspace it was closed in. If that workspace was closed, the entry is
  dropped (unless a workspace entry restores it first, see below). If it is hibernated, the entry is skipped but kept,
  so undo continues with the older entries and, once the workspace wakes, that entry is the next one to be reopened.
- A workspace entry (`closeWorkspace`) is a snapshot of the whole `Workspace` (pane tree, tabs, title, color, icon,
  group, actions, hibernation) plus its index in the bar. Undo puts it back at that index and selects it. It is
  skipped when a workspace with that id is already open.

A workspace that folds away because its last tab closed (`emptyWorkspaceToClose`) is the common way to lose one by
accident. `closeTab` flags the entry `lastOfWorkspace` when it empties the workspace, and `captureClosedWorkspace`
folds that tab back into the snapshot, so one undo returns the workspace with its tab instead of an empty shell.
`clearStaleFolds` drops the flag as soon as the workspace holds a tab again, so a later close never folds an older
tab by mistake. An empty workspace with no actions is not recorded. Tabs closed before the workspace stay as tab
entries below it and reopen into the restored workspace on the following undos.

A restored workspace gets fresh tab ids (`reviveWorkspace`): the old ones carry marks that outlive the close
(abandoned editor buffers, agent records). Editors come back clean,
floating browsers docked. A hibernated workspace keeps its terminal ids, because its stored agent sessions are
indexed by them and the wake-up looks them up. `tab.reopenClosed` is enabled while the active workspace is
hibernated, since it acts on the stack and not on that workspace. Resetting the workspaces (`resetWorkspaces`)
empties the stack.

### 5.8 Workspace authorization and file opening

A file opened in the editor from a directory the user has not navigated to in a terminal tab will show git diff decorations only after the directory is authorized. The source control panel will similarly refuse to operate on that path. Navigate to the directory in a terminal tab first (`cd <path>`) to authorize it.

### Tab kinds (tagged union)

`terminal` | `editor` | `browser` | `markdown` | `git-diff` | `git-history` | `git-commit-file`

All tab kinds follow the same never-unmount rule. Tabs live inside panes; panes are nodes of a binary split tree inside a workspace. The workspace bar (left, 52px) lists workspaces; the `Sidebar` holds Explorer, Source Control, Git History, and Notes (conditional on the workspace having a
`workspaceRoot`) and can dock left or right.

Every editor (and `markdown`) panel renders a thin top bar (`EditorPathBar`) as the first row of its layout: the open file's full path as a navigable breadcrumb on the left, and the editor controls on the right. The breadcrumb (`EditorPathBreadcrumb`, modeled by the pure `buildEditorPathBreadcrumb`) renders every directory segment as a clickable button that reveals that folder in the explorer; the filename is the non-clickable leaf. Each segment is tagged relative to the workspace root (`workspaceRoot`/`home` reach the bar via `EditorChromeContext`): the root segment carries a pin icon, its ancestors are dimmed, and descendants render normally; marking is suppressed when there is no pinned root or the file lives outside it. The full path is always shown (no segment collapsing) and the breadcrumb scrolls horizontally when it overflows, while the right-side controls stay fixed. Markdown files open in Live Preview (`kind: "markdown"`), whose bar carries the Source / Rich / Preview mode buttons and the Outline toggle. The bar also hosts a `[...]` dropdown that surfaces the per-extension view settings (wrap, line numbers, whitespace, fold gutter) for the currently open file extension; the header label reads "Applies to .<ext> files" and changes persist to `editorViewByExt` in the preferences store. Word wrap is a per-extension setting, not a global per-panel override. The file-name leaf has a right-click context menu (`FileLeafContextMenu` / `fileLeafMenuItems` in `modules/workspaces/pathbar/`): Reveal in Finder, Rename, Duplicate, Copy Absolute/Relative Path, Add to .gitignore, Delete. Mutations (rename/duplicate/delete) route through `RevealRequest.pendingAction` (an optional field added to `RevealRequest` in `src/modules/explorer/lib/pendingAction.ts`); `onFocusOnExplorer(path, action?)` in `App.tsx` sets the action when building the reveal request, and `FileExplorer.applyRevealTarget` performs it after revealing the path in the tree (nonce-guarded, fires once). Directory segments share the same `DirSegmentContextMenu` used by `TerminalPathBar`.

A `browser` panel carries an optional `floating` flag. When set, the panel is shown in a native `WebviewUrl::External` window (managed Rust-side by `FloatBrowserState`) and its in-pane slot renders a placeholder with an editable address bar instead of the iframe. See `docs/FORK.md` (Floating browser windows) for the full lifecycle.

Contains typed wrappers for all Tauri `invoke()` calls (`native.readFile`, `native.gitCommit`, `native.workspaceAuthorize`, etc.). All modules import from `@/lib/native` - never use `invoke()` directly in components or hooks.

## 8. Security model

**IPC boundary.** The WebView cannot access the filesystem, spawn processes, or make outbound HTTP requests directly. Every OS operation is an explicit `invoke()` call to a named Tauri command. The `capabilities/default.json` file is the allowlist - only commands listed there are available to the webview.

**Path authorization.** Git commands and shell operations require the target directory to be in the `WorkspaceRegistry`. The registry is populated by explicit user gestures (opening a directory, navigating there in a terminal) or by the CLI launch argument.

**Opening paths with the default app.** `capabilities/default.json` grants `opener:allow-open-path` with the scopes `**` and `/**`, so the webview can ask the OS to open any path. This is deliberate: a Tauri scope is a fixed list of glob patterns and cannot follow the workspace roots, and the only caller is "Open with Default App" in the explorer and git file menus (`explorer/lib/contextActions.tsx`), where the path comes from an explicit user gesture on a file the user can already see. The consequence is the same as double-clicking in Finder: a file whose default app executes it (`.command`, `.app`, `.terminal`, `.workflow` on macOS) runs when opened. Kex adds no confirmation for those types. If the webview ever shows untrusted file names or opens paths it did not get from a user gesture, narrow this scope or move the call behind a Rust command that validates the path.

**CSP.** The WebView has a strict Content Security Policy (see `tauri.conf.json`). `connect-src` allows `self`, Tauri IPC, and `https:` plus `http://localhost:*` (for local dev servers). `script-src` allows `wasm-unsafe-eval` (required for xterm.js WebGL). No `unsafe-eval`.

**OSC trust.** Kex processes OSC 7, OSC 133, and OSC 0/2 sequences. OSC 0/2 (window/icon title) is passed through as-is and shown in the pane tab; it is the only channel that updates the tab title at runtime. There is no OSC-based execution primitive (unlike iTerm2's proprietary sequences). The risk is cwd spoofing from maliciously crafted output, not code execution.
